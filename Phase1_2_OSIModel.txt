# Topic 2 — OSI and TCP/IP Models

> **Adaptation note:** This topic is conceptual — a model, not a feature. The 14-part structure applies, but where "previous implementation vs modern implementation" refers to *code*, I'll use *architecture of a pre-layered vs layered networking stack* instead. I'll flag this when it happens.

## The practical problem

Your React app sends a request to your ASP.NET Core API:

```
React Application
       |
       | HTTP Request
       v
ASP.NET Core API
```

What actually happens between them?

1. The application must format an HTTP request.
2. The request must be transported between computers.
3. The destination computer must be identified.
4. The correct network must be reached.
5. The correct application must receive the data.
6. The data must arrive in a format the receiver understands.

Six different engineering responsibilities.

**The fundamental problem:** How do we standardize communication so that applications, operating systems, network devices, and vendors can interoperate?

React on Windows. API on Linux. In Azure. Behind a router, a firewall, a switch. **All these must cooperate.**

---

## 1. WHY — Why were networking layers required?

### Without layering

Every application would need to understand every layer:

```
Application
    |
    |  Manually create packets
    |  Manually handle addressing
    |  Manually handle retransmission
    |  Manually handle physical signals
    v
Network
```

That is **impossible to build, maintain, and interoperate.**

### With layering

Each layer has **one responsibility** and **talks only to the layers above and below it**:

```
Application          →  "I want to send a JSON body"
Transport            →  "I'll deliver an ordered byte stream"
Network              →  "I'll route packets between networks"
Data Link            →  "I'll deliver frames within a LAN"
Physical             →  "I'll encode bits on the medium"
```

### Analogy — sending an international parcel

| Parcel delivery | Networking |
|---|---|
| Write the letter | Create application data |
| Put it in an envelope | Add transport info |
| Add the address | Add network address |
| Pack it in a shipping box | Add link-layer info |
| Hand to courier | Transmit over physical media |

Each stage adds what only it knows. Each receiver reverses the process.

**Layering exists because no single component can own every networking responsibility, and every component must be replaceable without breaking the others.**

---

## 2. BEFORE — What existed previously?

### Vendor-specific networking (1960s–1970s)

Each vendor implemented its own protocol stack:

- **IBM** — SNA (Systems Network Architecture)
- **DEC** — DECnet
- **Honeywell** — DSA (Distributed Systems Architecture)
- **Burroughs** — BNA

A DECnet network could not talk to an IBM SNA network. Getting them to exchange data required a **gateway** — a purpose-built translator, expensive and fragile.

```
Vendor A Computer
       |
 Vendor A Protocol
       |
 Vendor A Network

   [gateway — bespoke, fragile]

Vendor B Network
       |
 Vendor B Protocol
       |
Vendor B Computer
```

### The historical fork

Two standardization efforts emerged, for different reasons:

- **OSI model** (ISO, 1984) — a *general reference architecture*. Formally complete, theoretically elegant. Defined everything from electrical signaling to application protocols.
- **TCP/IP** (DARPA/ARPANET, 1970s–80s) — a *practical protocol suite* that evolved from working code. Less formally complete; won because it shipped, worked, and had a free implementation (BSD).

**This fork still matters:** OSI teaches reasoning. TCP/IP runs the world.

### Strengths of the old (pre-layering) approach

- **Optimized for one vendor** — hardware and software tuned together.
- **Deterministic** — no negotiation with foreign implementations.
- **No generalization cost** — no abstraction overhead.

These strengths are why specialized environments (industrial fieldbus, automotive CAN, avionics ARINC 429) still use non-IP protocols.

---

## 3. PROBLEM — Why was the old approach insufficient?

| Problem | Real impact |
|---|---|
| **Tight coupling** | Applications depend on hardware and vendor protocols |
| **Vendor lock-in** | Can't mix IBM, DEC, and modern systems |
| **No reusability** | Every app reimplements transport, addressing, retransmission |
| **Unmaintainable** | Changing one part breaks ten others |
| **Untestable in isolation** | Can't swap a cable without rewriting the app |
| **Slow innovation** | A better medium can't be adopted without rewriting everything |
| **Troubleshooting chaos** | A failure could be anywhere — no boundaries to narrow the search |

**Layering solves this through separation of concerns.** The killer example:

> Your ASP.NET Core application doesn't implement TCP retransmission. The OS does.  
> Your application doesn't know whether the physical medium is copper, fiber, or Wi-Fi. The lower stack does.

Change the physical medium → application unchanged. That is the payoff.

---

## 4. WHAT — The OSI model

**OSI** = Open Systems Interconnection. A **7-layer conceptual reference model** describing networking responsibilities.

| # | Layer | Responsibility | Examples |
|---|---|---|---|
| 7 | **Application** | Network services for applications | HTTP, DNS, SMTP, FTP |
| 6 | **Presentation** | Data representation and transformation | Encoding, serialization, compression |
| 5 | **Session** | Dialog and session management | Session coordination, checkpoints |
| 4 | **Transport** | End-to-end transport between processes | TCP, UDP |
| 3 | **Network** | Logical addressing and routing | IP, ICMP |
| 2 | **Data Link** | Local network delivery and framing | Ethernet, Wi-Fi MAC |
| 1 | **Physical** | Transmission of raw bits | Electrical, optical, radio |

### Brief tour of each layer

**Layer 7 — Application.** The protocol your application speaks. `HttpClient.GetAsync(...)` speaks HTTP at Layer 7. HTTP defines methods, headers, status codes, request/response structure.

**Layer 6 — Presentation.** Encoding (UTF-8), serialization (JSON, Protobuf), compression (gzip, brotli). **Caveat:** in real TCP/IP stacks, these are implemented in different places — TLS in a library, compression at the application or transport, serialization in the app. There is no distinct "Presentation layer" process running in your OS.

**Layer 5 — Session.** Conceptually, dialogue management. **Caveat:** modern HTTP sessions are application-level (cookies, tokens), not the OSI Session Layer. gRPC streams, WebSocket connections — all application-level sessions.

**Layer 4 — Transport.** TCP and UDP. **Ports belong here.** `10.10.1.20:50000 → 10.10.2.30:443`. TCP provides reliable, ordered delivery; UDP provides datagrams with no guarantees. TCP doesn't know the bytes are a payment — it delivers an ordered byte stream.

**Layer 3 — Network.** IP. Logical addressing and routing between networks. Routers operate here — they look at destination IP and choose the next hop.

**Layer 2 — Data Link.** Frames, MAC addresses, Ethernet, Wi-Fi. Switches operate here — they forward frames based on MAC address within a LAN.

**Layer 1 — Physical.** Bits encoded as electrical, optical, or radio signals. Cables, connectors, frequencies.

---

## 5. FEATURES — What does layering provide?

| Feature | What it achieves |
|---|---|
| **Separation of concerns** | Each layer has one responsibility |
| **Standardization** | Different vendors can interoperate |
| **Modularity** | Implementations evolve independently |
| **Abstraction** | Applications don't need hardware knowledge |
| **Troubleshooting** | Problems can be isolated by layer |
| **Reusability** | Common networking functionality is reused |
| **Substitutability** | Change copper → fiber; app unchanged |

**The practical test:** replace the Ethernet cable with Wi-Fi on a laptop. Your ASP.NET Core app doesn't change. That's the value of layering.

---

## 6. COMPARISON — Before vs after layering

The master prompt asks for a 10-dimension comparison. The comparison that matters here is **monolithic, application-owned networking** vs **the layered stack**.

| Dimension | Monolithic (pre-layering) | Layered (post-layering) |
|---|---|---|
| **Architecture** | Single application code owns every concern | Responsibilities divided across 4–7 layers |
| **Working mechanism** | App crafts packets, manages addressing, handles retransmission | App speaks HTTP; OS/libraries handle the rest |
| **Performance** | Potentially faster (no abstraction) — but only if hand-tuned by experts | Small abstraction overhead; far faster in practice because each layer is specialized and optimized |
| **Scalability** | App must be rewritten for each new medium or vendor | Any layer can scale independently |
| **Reliability** | Each app invents its own retransmission — inconsistent, often buggy | TCP provides uniform reliability for everyone |
| **Security** | Every app reimplements encryption — likely insecure | TLS provided once, by experts |
| **Complexity** | Simple in a single scope, catastrophic across vendors | Moderate per layer, manageable overall |
| **Maintenance** | Changes ripple through the whole app | Layers evolve independently |
| **Cost** | Cheap for one app, ruinous at scale | Higher upfront design cost, far lower total cost |
| **Failure handling** | Failures are app-specific and unknowable | Failures are diagnosable per layer |

**Why it changed:** the monolith optimizes a single application. The layered model optimizes an **ecosystem**. The internet is an ecosystem — that's why it won.

### OSI vs TCP/IP — the model comparison

| OSI | TCP/IP | Examples |
|---|---|---|
| Application | **Application** | HTTP, DNS, SMTP |
| Presentation | (folded into Application) | JSON, TLS-adjacent |
| Session | (folded into Application) | Session management |
| Transport | **Transport** | TCP, UDP |
| Network | **Internet** | IP, ICMP |
| Data Link | **Network Access** | Ethernet, Wi-Fi |
| Physical | (folded into Network Access) | Cable, fiber, radio |

**Don't assume TCP/IP lacks presentation, session, or encryption.** They exist — inside libraries and protocols. The 4-layer model simply doesn't call them out as separate layers.

**Why the difference:** OSI is a **conceptual reference** — pedagogical granularity. TCP/IP is an **implemented architecture** — practical grouping. OSI teaches you to *reason*; TCP/IP shows you what *runs*.

---

## 7. ADVANTAGES AND DISADVANTAGES

### Advantages of layering
- **Interoperability** — multi-vendor systems work
- **Reusability** — one TCP stack serves all apps
- **Substitutability** — swap media, protocols, or vendors without breaking others
- **Diagnosability** — failures narrow to a layer
- **Independent evolution** — HTTP/3 can arrive without touching Ethernet

### Disadvantages and hidden costs
- **Abstraction cost** — each layer adds headers, buffering, and processing
- **Obfuscation** — the higher you are, the less you see about what's really happening
- **Latency stacking** — 5 layers × (parse, buffer, validate) × N hops = measurable overhead
- **Debugging across layers** — a slow API call might be TCP retransmits, MTU, TLS, or the app
- **Leaky abstractions** — every abstraction eventually leaks; you'll still need to know what's underneath
- **Configuration burden** — 7 layers × 2 stacks × N servers = substantial config surface

### When the old, non-layered approach is still correct
- **Air-gapped industrial control** — fieldbus, Modbus, CAN. Determinism beats generality.
- **Real-time hard loops** — automotive, aviation, medical. Protocol overhead is unacceptable.
- **Embedded microcontrollers** — a 2 KB RAM sensor doesn't run a full TCP/IP stack. It speaks a minimal protocol.
- **Latency-critical trading hot paths** — some use raw UDP with custom reliability on kernel-bypass NICs, not the general TCP stack.

**Honest take:** the layered model is right for the 99% — but a Principal Engineer knows the 1% where it isn't.

---

## 8. WHEN — When to use these models?

You don't select "OSI or TCP/IP" when building software. You use them as **troubleshooting and reasoning tools**.

| Symptom | Layer to investigate first |
|---|---|
| Cable disconnected, no link LED | 1 — Physical |
| Switch port down, VLAN mismatch | 2 — Data Link |
| Wrong IP / route missing | 3 — Network |
| TCP connection refused | 3–4 — Network / Transport |
| TLS handshake fails | Often Layers 5–7 (application-facing stack) |
| HTTP 404 | 7 — Application |
| JSON deserialization error | 7 — Application |

**Caveat:** real failures can span layers. A TLS failure may be a cert issue, a clock mismatch, a missing CA, or a middlebox. **Use the model to narrow — not to conclude.**

## 9. HOW — Practical implementation

### A. Previous implementation — application owns everything

```
Application
    |
    |  Craft packet headers manually
    |  Handle addressing
    |  Retransmit on loss
    |  Encode bits to signals
    v
Network
```

This is what proprietary trading and embedded systems still do. It's fast but inflexible and error-prone.

### B. Modern implementation — use networking abstractions

```csharp
using System.Net.Http;

var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(10)
};

using var client = new HttpClient(handler);
var response = await client.GetAsync("https://example.com/api/accounts");
response.EnsureSuccessStatusCode();

var result = await response.Content.ReadAsStringAsync();
Console.WriteLine(result);
```

**What each part maps to:**

| .NET component | Networking responsibility |
|---|---|
| `HttpClient` | HTTP (Layer 7) |
| `SocketsHttpHandler` | HTTP + TCP (Layers 4–7 glue) |
| Sockets API | OS networking (Layers 3–4) |
| OS TCP/IP stack | Layers 3–4 |
| NIC driver | Layers 1–2 |
| Router | Layer 3 |
| Switch | Layer 2 |
| Physical medium | Layer 1 |

**Production note:** use `IHttpClientFactory` or a properly managed long-lived `HttpClient` — do **not** create and dispose a new `HttpClient` per request. That exhausts TCP ports and breaks connection pooling. (Topic 30 covers why.)

## 10. INTERNAL WORKING — Encapsulation and decapsulation

**This is the single most important section of the topic.**

### Sending side — encapsulation

```
HTTP request:  "GET /api/accounts/123 HTTP/1.1"
              ↓
Add TCP header: [TCP hdr | HTTP data]        ← Segment
              ↓
Add IP header:  [IP hdr | TCP hdr | data]    ← Packet
              ↓
Add Eth header: [Eth hdr | IP pkt | FCS]     ← Frame
              ↓
Encode:         101100101010...              ← Bits
```

### PDU names (memorize)

| Layer | PDU |
|---|---|
| Application | Data / Message |
| Transport — TCP | **Segment** |
| Transport — UDP | **Datagram** |
| Network | **Packet** |
| Data Link | **Frame** |
| Physical | **Bits** |

**PDU** = Protocol Data Unit.

### Receiving side — decapsulation

```
Bits → Frame → Packet → Segment → HTTP request → ASP.NET Core endpoint
```

Each layer strips its own header and passes the payload up.

### Real-world nuance — TLS in the stack

Plain HTTP/1.1 or HTTP/2:

```
HTTP
  |
TLS
  |
TCP
  |
IP
  |
Ethernet / Wi-Fi
```

HTTP/3:

```
HTTP/3
   |
QUIC  (includes TLS 1.3 integration)
   |
UDP
   |
IP
   |
Ethernet / Wi-Fi
```

We'll study these differences at Topics 8 and 24.

## 11. FAILURE SCENARIOS — Where devices operate

| Device | Main layer | What it examines |
|---|---|---|
| Hub / repeater | 1 | Physical signals |
| Layer 2 switch | 2 | MAC addresses |
| Router | 3 | IP addresses |
| Layer 4 firewall | 3–4 | IPs, protocols, ports, connection state |
| Layer 7 firewall / WAF | 7 | Application protocols and payloads |

Some devices span layers. A modern firewall inspects Layers 3–7. A Layer 3 switch routes IP and switches Ethernet frames.

### Example failures

**Switch problem — two LAN hosts can't communicate.** VLAN misconfig, port disabled, MAC learning issue, cable fault. Investigate **Layers 1–2**.

**Router problem — has IP but can't reach a remote network.** Missing route, wrong gateway, router failure, ACL block. Investigate **Layer 3**.

**TCP problem — can't connect to port 443.** Firewall, not listening, route unavailable, RST. Investigate **Layers 3–4**.

**HTTP problem — TCP connects, returns 404.** Path and TCP are fine. Problem is **Layer 7**.

### Diagnostic commands (Windows PowerShell)

```powershell
ipconfig /all                              # Layer 1–3 config
ping 8.8.8.8                               # Layer 3 reachability
nslookup example.com                       # Application (DNS)
Test-NetConnection example.com -Port 443   # Layer 4 TCP
tracert example.com                        # Layer 3 path
```

**Golden rule:** **Don't assume an HTTP failure is a network failure. First identify the failing layer.**

```
      [ React Trading UI ]
              |
           HTTP / TLS
              |
      [ Load Balancer / WAF ]
              |
       IP routing + TCP
              |
      [ ASP.NET Core Trading API ]
              |
     +--------+--------+
     |                 |

```

| Component | Networking responsibility |
|---|---|
| React | Creates HTTP request (L7) |
| TLS | Protects communication |
| TCP | Reliable ordered transport (L4) |
| IP | Addresses and routes packets (L3) |
| Ethernet / Wi-Fi | Frames on local link (L2) |
| Switch | Forwards frames (L2) |

### Principal Engineer considerations — "the API is slow"

Diagnose layer by layer:

1. **Network latency high?** — traceroute, RTT measurements.
2. **TCP establishment slow?** — SYN retransmits, listen backlog, TLS session reuse.
3. **TLS negotiation slow?** — handshake count, key exchange, cert chain.
4. **API processing slow?** — GC, thread pool, lock contention.
5. **Database slow?** — connection pool, query plans.
6. **Kafka wait?** — consumer lag, producer backpressure.

**Do not autoscale the API because users say it's slow.** The bottleneck may be in a layer or dependency you can't see from the app.

## 13. PRINCIPAL ENGINEER PERSPECTIVE

**1. Layers abstract — they don't isolate.** A lower-layer failure affects every layer above it. NIC loses link → HTTP fails.

**2. Lower-layer success ≠ higher-layer success.** Ping works → TCP may still fail → TLS may still fail → HTTP may still fail. **Three diagnostic layers, always climb in order.**

**3. The model is a troubleshooting tool, not dogma.** Use it to *narrow* — not to *conclude*.

**4. Application-level sessions ≠ OSI Session Layer.** Related, not identical. Don't confuse them in a design review.

**5. Encapsulation is the mental model for microservices.** Two microservices do not exchange C# objects. They exchange serialized bytes over HTTP/gRPC over TCP over IP over Ethernet. Every hop, every layer, every header.

### Anti-patterns
- "The network is fine because ping works."
- Skipping TLS verification "just in production."
- Assuming container co-location means reachability (it doesn't — no network path, wrong port, wrong network namespace).
- Ignoring layer boundaries when designing retries — retrying at L7 without understanding L4/L3 failures duplicates work and amplifies load.

## 14. INTERVIEW AND KNOWLEDGE VALIDATION — with explanations

### Basic

**Q1. What is the OSI model?**  
A **seven-layer conceptual reference model** from ISO that divides network communication into distinct responsibilities: Application, Presentation, Session, Transport, Network, Data Link, Physical. It is not an implementation — it is a teaching and troubleshooting framework. Its value is that it gives engineers a **shared vocabulary** to describe *where* a problem lives.

**Q2. How many layers does TCP/IP have?**  
The **commonly taught TCP/IP model has four layers**: Application, Transport, Internet, Network Access. The original RFC 1122 is consistent with this. Some textbooks use a **five-layer** variant (Physical, Data Link, Network, Transport, Application) to align better with OSI. Either way, the model describes the stack that actually runs — not a conceptual reference.

**Q3. What is encapsulation?**  
The process of **adding a layer-specific header as data moves down the stack**. Application data → TCP segment → IP packet → Ethernet frame → bits. Each layer prepends its own control information. The receiver performs **decapsulation** — stripping headers in reverse order. Encapsulation is how a single byte stream can traverse physically different media while carrying consistent semantics.

### Intermediate

**Q4. What is the difference between a TCP segment and an IP packet?**  
A **TCP segment** = TCP header + application data. It carries **port numbers, sequence numbers, acknowledgement numbers, flags** — it knows about *processes*. An **IP packet** = IP header + payload (which is usually a TCP segment). It carries **source and destination IP addresses** — it knows about *hosts*. An IP packet can be fragmented or rerouted without TCP knowing; a TCP segment is a fixed conceptual unit that TCP counts and acknowledges. **TCP thinks in segments; IP thinks in packets.**

**Q5. Why does a switch primarily operate at Layer 2?**  
A Layer 2 switch forwards **Ethernet frames using MAC addresses**. It maintains a **MAC address table** (CAM table) mapping ports to MAC addresses, learns by observing source MACs, and floods unknown destinations out all ports. It does not inspect IP addresses — it doesn't need to. Its job is **within a LAN**, and MAC addressing is sufficient there.

**Q6. Why does a router operate at Layer 3?**  
A router **forwards IP packets between networks** using **destination IP addresses and a routing table**. MAC addresses are local to a link; a router needs logical addressing that spans links. Its job is to answer: *which network is this packet headed to, and what's the next hop?* That's Layer 3.

### Advanced

**Q7. If ping works but an HTTPS API call fails, does that mean the network is working?**  
**No — it means Layer 3 reachability exists.** ICMP echo replies prove the host responds to ICMP. They do **not** prove: (a) TCP port 443 is listening, (b) a firewall permits TCP, (c) TLS handshake succeeds (cert, SNI, time, cipher), (d) HTTP request is valid, (e) the app is responsive. **Reachability ≠ availability.** Always climb Layers 3 → 4 → 7 when diagnosing.

**Q8. Why does TCP/IP combine the OSI Session, Presentation, and Application layers?**  
Because **TCP/IP was designed from working implementations, not theory.** ARPANET engineers shipped code first; the model followed. Session and presentation functions — session management, encoding, compression — were implemented **inside application protocols** (HTTP cookies, TLS, gzip in HTTP). There was never a separate running process at OSI Layers 5–6 in a TCP/IP host. **TCP/IP groups what actually coexists in the same software.**

**Q9. Can a firewall operate at multiple OSI layers?**  
**Yes — and modern ones do.** A basic **packet filter** inspects IPs, protocols, and ports (Layers 3–4). A **stateful firewall** tracks connection state (Layer 4). An **application-aware firewall / WAF** inspects HTTP headers, URLs, payloads (Layer 7). A modern enterprise firewall spans **Layers 3–7**. The OSI model doesn't force one layer per device — it forces *clarity about what a device inspects*.

### Scenario-based

**Q10. Your API returns 504 Gateway Timeout. Which layer is likely failing?**  
**504 indicates the gateway (e.g., reverse proxy, load balancer) did not receive a timely response from the upstream.** The network path *to* the gateway worked (otherwise 502 or connection refused). The gateway's connection *to* the backend likely succeeded or stalled. Most likely causes: **backend app hung (Layer 7), backend TCP accepted but never responded (Layers 4–7), or backend dependency slow (DB/queue)**. Not usually Layer 1–3 — the gateway is on the same network segment as the backend.

**Q11. A message arrives at the wrong application on the same server. Which layer failed?**  
**Layer 4 — Transport.** The port mapping directed the data incorrectly. IP (Layer 3) delivered to the right host; TCP (Layer 4) delivered to the wrong port. This is exactly why **ports exist** — to distinguish applications on the same host. If the ports were swapped, the OS delivered the segment to whichever socket was bound to that port.

**Q12. Trace a request from `HttpClient.PostAsync` to a stored SQL row. Name every layer at each hop.**  
- **App (L7)** — `HttpClient` serializes the request into HTTP.
- **TLS** — encrypts the bytes.
- **TCP (L4)** — segments, adds ports, sequence numbers.
- **IP (L3)** — adds source/dest IPs.
- **Ethernet (L2)** — adds MAC addresses; the switch forwards.
- **Physical (L1)** — bits on the wire.
- **Routers** — switch IP packets hop-by-hop (L3).
- **Receiving side reverses** — decapsulate to HTTP, then app code, then SQL driver → TCP → DB, and reverse again for the response.

Each hop is a layer boundary; each boundary is a **potential point of failure**.

# TCP/IP layers: what each does and what you can do from C#

This combines the earlier answers into one map. I use the 4-layer TCP/IP model and note the OSI equivalents.

| TCP/IP layer | OSI | Your access from code |
|---|---|---|
| **Application** | 7, 6, 5 | Full |
| **Transport** | 4 | Partial (choose TCP/UDP/QUIC, tune options) |
| **Internet** | 3 | Limited (TTL, DSCP, ICMP, raw sockets) |
| **Link** | 2 | Read-only normally, or capture with a library |
| **Physical** | 1 | Read link status only |

---

## 1. Application layer (OSI 7, 6, 5)

Everything here is plain library code. It has three sub-jobs.

### 1a. Protocol: HTTP, DNS, WebSocket (OSI 7)

```csharp
// HTTP client: headers, cookies, redirects, auto-decompression
var handler = new SocketsHttpHandler
{
    UseCookies = true,
    CookieContainer = new CookieContainer(),
    AllowAutoRedirect = true,
    AutomaticDecompression = DecompressionMethods.GZip | DecompressionMethods.Brotli
};
var client = new HttpClient(handler) { Timeout = TimeSpan.FromSeconds(10) };
client.DefaultRequestHeaders.Add("X-Correlation-Id", Guid.NewGuid().ToString());
var res = await client.GetAsync("https://api.example.com/users");

// HTTP server: routes, status codes, headers, cookies
app.MapGet("/login", (HttpContext ctx) =>
{
    ctx.Response.Cookies.Append("sid", "xyz",
        new CookieOptions { HttpOnly = true, Secure = true, SameSite = SameSiteMode.Strict });
    ctx.Response.Headers["Cache-Control"] = "no-store";
    return Results.Ok();
});

// DNS
var ips  = await Dns.GetHostAddressesAsync("example.com");
var host = await Dns.GetHostEntryAsync("8.8.8.8");        // reverse lookup

// WebSocket (persistent two-way channel, still Application layer)
using var ws = new ClientWebSocket();
await ws.ConnectAsync(new Uri("wss://example.com/chat"), CancellationToken.None);
await ws.SendAsync(Encoding.UTF8.GetBytes("hi"), WebSocketMessageType.Text, true, CancellationToken.None);
```

### 1b. Presentation: serialization, compression, encoding, encryption (OSI 6)

```csharp
// Serialization
string json = JsonSerializer.Serialize(new { Name = "Ravi", Age = 30 });
var obj = JsonSerializer.Deserialize<User>(json);

// Character encoding
byte[] bytes = Encoding.UTF8.GetBytes("héllo");

// Compression
using var gz = new GZipStream(outStream, CompressionMode.Compress);
using var br = new BrotliStream(outStream, CompressionMode.Compress);
builder.Services.AddResponseCompression();   // server-side, then app.UseResponseCompression()

// Base64 / binary representation
string b64 = Convert.ToBase64String(bytes);

// TLS configuration (encryption of the data stream)
var tlsHandler = new SocketsHttpHandler
{
    SslOptions = new SslClientAuthenticationOptions
    {
        EnabledSslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13,
        ClientCertificates = new X509CertificateCollection { myCert },   // mutual TLS
        ApplicationProtocols = new() { SslApplicationProtocol.Http2 },   // ALPN
        RemoteCertificateValidationCallback = (s, cert, chain, errors) =>
            errors == SslPolicyErrors.None
    }
};

// Server-side TLS
builder.WebHost.ConfigureKestrel(k =>
    k.ConfigureHttpsDefaults(h =>
    {
        h.SslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13;
        h.ClientCertificateMode = ClientCertificateMode.RequireCertificate;
    }));
```

### 1c. Session: user-session state (OSI 5, really Application)

```csharp
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = "localhost:6379");
builder.Services.AddSession(o =>
{
    o.IdleTimeout = TimeSpan.FromMinutes(20);
    o.Cookie.Name = ".app.session";
    o.Cookie.HttpOnly = true;
    o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    o.Cookie.SameSite = SameSiteMode.Lax;
});
app.UseSession();

app.MapGet("/cart", (HttpContext ctx) =>
{
    ctx.Session.SetString("userId", "42");     // stored in Redis, keyed by the cookie's session ID
    return ctx.Session.GetString("userId");
});

// Alternative: stateless cookie auth or JWT (no server-side session store)
builder.Services.AddAuthentication().AddCookie();
```

Sticky sessions are not in your code. They are load-balancer config (nginx `ip_hash` or cookie affinity, ALB stickiness). TLS session resumption is automatic in the runtime and OS.

## 2. Transport layer (OSI 4): TCP, UDP, QUIC

You choose the protocol, port and behavior. The kernel runs the state machine, retransmission and congestion control.

### Via HTTP code (no manual sockets)

```csharp
var handler = new SocketsHttpHandler
{
    ConnectTimeout = TimeSpan.FromSeconds(3),
    PooledConnectionLifetime = TimeSpan.FromMinutes(5),
    PooledConnectionIdleTimeout = TimeSpan.FromMinutes(1),
    MaxConnectionsPerServer = 20,
    EnableMultipleHttp2Connections = true,
    KeepAlivePingDelay = TimeSpan.FromSeconds(30),        // HTTP/2 pings keep the TCP connection alive
    KeepAlivePingTimeout = TimeSpan.FromSeconds(10)
};

// HTTP/3 = QUIC over UDP, with no socket code from you
var req = new HttpRequestMessage(HttpMethod.Get, url)
{
    Version = HttpVersion.Version30,
    VersionPolicy = HttpVersionPolicy.RequestVersionOrLower
};

// Kestrel: ports, protocols, connection limits
builder.WebHost.ConfigureKestrel(k =>
{
    k.ListenAnyIP(8443, o =>
    {
        o.Protocols = HttpProtocols.Http1AndHttp2AndHttp3;
        o.UseHttps();
    });
    k.Limits.MaxConcurrentConnections = 1000;
    k.Limits.KeepAliveTimeout = TimeSpan.FromMinutes(2);
    k.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(30);
});
```

### Hook into the socket HttpClient uses

```csharp
var handler = new SocketsHttpHandler
{
    ConnectCallback = async (ctx, ct) =>
    {
        var s = new Socket(SocketType.Stream, ProtocolType.Tcp) { NoDelay = true };
        s.SetSocketOption(SocketOptionLevel.Socket, SocketOptionName.KeepAlive, true);
        s.SetSocketOption(SocketOptionLevel.Tcp, SocketOptionName.TcpKeepAliveTime, 60);
        s.SetSocketOption(SocketOptionLevel.Tcp, SocketOptionName.TcpKeepAliveInterval, 10);
        s.SetSocketOption(SocketOptionLevel.Tcp, SocketOptionName.TcpKeepAliveRetryCount, 3);
        await s.ConnectAsync(ctx.DnsEndPoint, ct);
        return new NetworkStream(s, ownsSocket: true);
    }
};
```

### Pure TCP, UDP and QUIC

```csharp
// TCP client and server (you invent the protocol)
using var tcp = new TcpClient { NoDelay = true, ReceiveTimeout = 5000, SendTimeout = 5000 };
await tcp.ConnectAsync("example.com", 9000);
var stream = tcp.GetStream();
await stream.WriteAsync(Encoding.UTF8.GetBytes("PING\n"));

var listener = new TcpListener(IPAddress.Any, 9000);
listener.Start(backlog: 100);                      // pending-connection queue size
var client = await listener.AcceptTcpClientAsync();

// Socket options
var s = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
s.ReceiveBufferSize = 64 * 1024;
s.SendBufferSize    = 64 * 1024;
s.LingerState = new LingerOption(true, 5);         // wait up to 5s for pending data on close
s.SetSocketOption(SocketOptionLevel.Socket, SocketOptionName.ReuseAddress, true);
s.Bind(new IPEndPoint(IPAddress.Any, 9001));       // choose the local port

// UDP: no handshake, no delivery guarantee
using var udp = new UdpClient(5000) { EnableBroadcast = true };
await udp.SendAsync(data, data.Length, "10.0.0.5", 5000);
var received = await udp.ReceiveAsync();

// Multicast: one sender, many receivers
udp.JoinMulticastGroup(IPAddress.Parse("239.1.1.1"));

// QUIC directly (check QuicConnection.IsSupported first)
if (QuicConnection.IsSupported) { /* QuicConnection.ConnectAsync(...) */ }

// Inspect what the OS has open
var props = IPGlobalProperties.GetIPGlobalProperties();
foreach (var c in props.GetActiveTcpConnections())
    Console.WriteLine($"{c.LocalEndPoint} -> {c.RemoteEndPoint} {c.State}");
```

**What you can't do:** change TCP's congestion algorithm per call, or implement retransmission. That's kernel territory (on Linux, `sysctl` or a `TCP_CONGESTION` socket option).

## 3. Internet layer (OSI 3): IP and ICMP

```csharp
// Address handling
var ip = IPAddress.Parse("192.168.1.10");
bool isV6 = ip.AddressFamily == AddressFamily.InterNetworkV6;
bool loopback = IPAddress.IsLoopback(ip);

// Pick IPv4 vs IPv6
var s4 = new Socket(AddressFamily.InterNetwork,   SocketType.Stream, ProtocolType.Tcp);
var s6 = new Socket(AddressFamily.InterNetworkV6, SocketType.Stream, ProtocolType.Tcp);

// IP header fields via socket options
s4.Ttl = 64;                    // hop limit
s4.DontFragment = true;         // set the DF flag
s4.SetSocketOption(SocketOptionLevel.IP, SocketOptionName.TypeOfService, 0xB8);  // DSCP/QoS (honored by Linux; Windows often ignores it)

// ICMP ping
var reply = await new Ping().SendPingAsync("8.8.8.8", 1000, new byte[32],
    new PingOptions(ttl: 64, dontFragment: true));
Console.WriteLine($"{reply.Status} {reply.RoundtripTime}ms");

// Traceroute: increment TTL until the destination answers
for (int ttl = 1; ttl <= 30; ttl++)
{
    var r = await new Ping().SendPingAsync("8.8.8.8", 2000, new byte[32],
        new PingOptions(ttl, true));
    Console.WriteLine($"{ttl}: {r.Address} ({r.Status})");     // TtlExpired = a router on the path
    if (r.Status == IPStatus.Success) break;
}

// MTU discovery: send with DF set and shrink the payload until it works
// (a Status of PacketTooBig means you exceeded the path MTU)

// Raw socket (admin/root): you build the IP/ICMP packet bytes yourself
var raw = new Socket(AddressFamily.InterNetwork, SocketType.Raw, ProtocolType.Icmp);
raw.Bind(new IPEndPoint(IPAddress.Any, 0));

// Interface IPs, gateway, DNS servers, routing context
foreach (var nic in NetworkInterface.GetAllNetworkInterfaces())
{
    var p = nic.GetIPProperties();
    foreach (var u in p.UnicastAddresses)
        Console.WriteLine($"{nic.Name}: {u.Address}/{u.PrefixLength}");
    foreach (var g in p.GatewayAddresses)
        Console.WriteLine($"  gateway {g.Address}");
}
```

**What you can't do (without raw sockets or admin tools):** edit routing tables, change fragmentation behavior, or choose the path a packet takes. That's the OS and router job (`route`, `ip route`, firewall and security-group config).

## 4. Link layer (OSI 2): Ethernet and Wi-Fi

Normal code only reads. Capture or crafting needs a library and admin rights.

```csharp
// Read NIC details (no privileges needed)
foreach (var nic in NetworkInterface.GetAllNetworkInterfaces())
{
    Console.WriteLine($"{nic.Name}  MAC={nic.GetPhysicalAddress()}  " +
                      $"Type={nic.NetworkInterfaceType}  Speed={nic.Speed / 1_000_000} Mbps");
    var stats = nic.GetIPStatistics();
    Console.WriteLine($"  bytes in={stats.BytesReceived} out={stats.BytesSent} errors={stats.IncomingPacketsWithErrors}");
}

// Capture frames with SharpPcap + PacketDotNet (NuGet; needs Npcap/libpcap and admin)
var dev = CaptureDeviceList.Instance[0];
dev.OnPacketArrival += (s, e) =>
{
    var raw = e.GetPacket();
    var pkt = Packet.ParsePacket(raw.LinkLayerType, raw.GetPacket().Data);
    var eth = pkt.Extract<EthernetPacket>();
    Console.WriteLine($"{eth.SourceHardwareAddress} -> {eth.DestinationHardwareAddress}");
};
dev.Open();
dev.StartCapture();
// (method names vary slightly between SharpPcap versions)

// Wake-on-LAN: a magic packet is a link-level concept, commonly sent as a UDP broadcast
byte[] mac = { 0xAA, 0xBB, 0xCC, 0xDD, 0xEE, 0xFF };
var magic = Enumerable.Repeat((byte)0xFF, 6)
    .Concat(Enumerable.Repeat(mac, 16).SelectMany(m => m)).ToArray();
using var wol = new UdpClient { EnableBroadcast = true };
await wol.SendAsync(magic, magic.Length, new IPEndPoint(IPAddress.Broadcast, 9));
```

ARP (IP to MAC) is done by the kernel. You can only read the cache, for example by running `arp -a`.

## End-to-end: one request, every layer

```csharp
var handler = new SocketsHttpHandler
{
    // L4/L3: socket-level tuning
    ConnectCallback = async (ctx, ct) =>
    {
        var s = new Socket(SocketType.Stream, ProtocolType.Tcp) { NoDelay = true, Ttl = 64 };
        await s.ConnectAsync(ctx.DnsEndPoint, ct);
        return new NetworkStream(s, true);
    },
    // L6: TLS and compression
    SslOptions = { EnabledSslProtocols = SslProtocols.Tls13 },
    AutomaticDecompression = DecompressionMethods.All,
    // L7/L5: cookies as session carrier
    UseCookies = true,
    CookieContainer = new CookieContainer()
};
var client = new HttpClient(handler);

// L7 request, L6 serialization
var res = await client.PostAsJsonAsync("https://api.example.com/orders", new { Item = "book" });
var body = await res.Content.ReadFromJsonAsync<Order>();
```

Here the kernel does IP routing, framing and the TCP handshake. The NIC and hardware do L2 and L1.

## Master summary

| Layer | Things you can do in code | API |
|---|---|---|
| **Application (7/6/5)** | HTTP calls, headers, cookies, sessions, DNS, WebSocket, JSON/XML, compression, encoding, TLS config, Redis session store | `HttpClient`, ASP.NET Core, `Dns`, `System.Text.Json`, `GZipStream`, `SslOptions` |
| **Transport (4)** | Choose TCP/UDP/QUIC/HTTP3, ports, timeouts, keep-alive, pooling, buffers, Nagle, linger, backlog, multicast, list connections | `SocketsHttpHandler`, Kestrel limits, `Socket`, `TcpClient`, `UdpClient`, `IPGlobalProperties` |
| **Internet (3)** | IPv4/v6, TTL, DF flag, DSCP, ping, traceroute, MTU probing, raw ICMP/IP, read IPs and gateways | `Ping`, `Socket` options, raw sockets, `NetworkInterface` |
| **Link (2)** | Read MAC, speed, stats; capture or craft frames with a library; Wake-on-LAN | `NetworkInterface`, SharpPcap |
| **Physical (1)** | Read link up/down and network-change events | `OperationalStatus`, `NetworkChange` |

Other stacks follow the same pattern. Java uses `HttpClient`, `Socket` and `StandardSocketOptions`. Python uses `requests`, `socket.setsockopt()` and Scapy for L2/L3. Node uses `http`, `net`, `dgram` and `dns`. In all of them, **L7/L6 is library code, L4/L3 is socket options, and L2/L1 is a capture library or OS tools.**
