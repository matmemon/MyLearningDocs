# **Azure Container Apps — Complete Learning Guide**

**Profile:** Loaded | **Topic:** Azure Container Apps | **Mode:** Full | **Blocks:** A–H | **Skipped:** Basic C#/.NET development — established through your 13+ years of .NET experience; Docker, AKS and Kubernetes fundamentals — assumed familiar, but key differences will be explained.

**Learning objective:** Understand why Azure Container Apps exists, how it works, how to build and operate .NET microservices on it, and—most importantly—when to choose it instead of App Service or AKS.

## **First, the simplest explanation**

Let's use your banking application as an example.

You have four independent services:

1. Customer API — receives customer requests.
2. Payment API — processes payments.
3. Notification Worker — sends SMS and emails.
4. Report Worker — generates reports in the background.

All four can run in Azure App Service. You do not need Container Apps just because you have four microservices.

But imagine this:

- Customer API receives web traffic.
- Payment API receives web traffic.
- Notification Worker waits for messages in Azure Service Bus.
- Report Worker runs only when a report is requested.

You want Azure to understand what each service is doing and scale it accordingly.

That's where Container Apps becomes particularly useful.

**Your banking application**

**Customer API**

Incoming HTTP requests → more replicas when traffic increases

**Payment API**

Incoming HTTP requests → independent scaling

**Notification Worker**

Service Bus messages → more worker replicas when queue grows

**Report Worker**

Scheduled or event-driven execution → runs when required

Azure Container Apps

**The central idea:** You give Azure your containerized applications. Azure manages the infrastructure needed to run them, and Container Apps provides built-in capabilities to scale individual workloads based on different signals.

It is not a replacement for every App Service workload, and it is not a replacement for every AKS workload.

## **BLOCK A — Opening answers**

### **A1. Preliminary 1-minute answer — v1**

Azure Container Apps is a managed platform for running containerized applications without having to manage Kubernetes clusters yourself.

You package your application into a Docker container and deploy it to Container Apps. Azure manages the underlying platform and provides features such as ingress, revisions, traffic splitting, autoscaling, managed identity, secrets and background jobs.

One of its important capabilities is event-driven scaling using KEDA. For example, a .NET worker can automatically scale based on the number of messages waiting in Azure Service Bus, and can scale to zero when there is no work, if configured.

It is useful for microservices, APIs, background workers and event-driven applications where you want container flexibility without operating AKS.

### **A2. Scenario index**

- Happy path — deploy and run a .NET microservice.
- Failure/recovery — container crashes or Service Bus becomes unavailable.
- 10× scale — sudden increase in payment and notification workloads.
- Security/compliance — managed identity, secrets and network isolation.
- Cost — consumption versus dedicated workload profiles.
- Migration/modernization — move from App Service or AKS.
- Monitoring/incident — diagnose failed replicas and slow requests.
- Alternatives — App Service, AKS and Functions.
- Enterprise/multi-team — multiple services, environments and ownership.
- Business case — why Container Apps instead of managing Kubernetes.

## **BLOCK B — Foundations**

### **B1. WHY does Azure Container Apps exist?**

Let's understand the problem before the technology.

**Imagine your company has 20 .NET microservices.**

Earlier, you might host applications on virtual machines.

Your responsibilities include:

- Creating and maintaining VMs.
- Installing operating systems.
- Installing Docker.
- Managing containers.
- Configuring networking.
- Handling scaling.
- Managing availability.
- Updating infrastructure.

This becomes difficult when the number of services increases.

You could use AKS, which provides Kubernetes orchestration. But now your team must understand and operate Kubernetes concepts such as:

- Clusters and nodes.
- Node pools.
- Pods and deployments.
- Services and ingress.
- Kubernetes networking.
- Cluster upgrades.
- Resource scheduling.

AKS is powerful, but it introduces operational responsibilities.

Container Apps addresses this middle ground:

**You want to deploy containers and get managed scaling and microservice capabilities without directly managing a Kubernetes cluster.**

### **B2. BEFORE Container Apps — what were the alternatives?**

| Approach         | What you manage                         | Limitation                                            |
| ---------------- | --------------------------------------- | ----------------------------------------------------- |
| Virtual Machines | OS, runtime, application and scaling    | More infrastructure work                              |
| Docker on VMs    | VMs, Docker and container lifecycle     | You manage orchestration                              |
| App Service      | Application hosting configuration       | Less specialized for event-driven container workloads |
| AKS              | Kubernetes infrastructure and workloads | More Kubernetes operational complexity                |
| Container Apps   | Container workload configuration        | Less low-level Kubernetes control                     |

Important: App Service was not incapable of running containers or multiple applications. It remains a valid choice.

### **B3. What problem does Container Apps solve?**

| Dimension         | Problem                                   | How Container Apps addresses it                  |
| ----------------- | ----------------------------------------- | ------------------------------------------------ |
| Container hosting | Need to host Docker images                | Runs container images                            |
| Scaling           | Different services have different demands | Independent replica scaling                      |
| Event processing  | Workers depend on queue messages          | KEDA-based event scaling                         |
| Idle workloads    | Paying for continuously running replicas  | Can scale to zero where supported and configured |
| Deployment        | Need safe releases                        | Revisions and traffic splitting                  |
| Microservices     | Services need to communicate              | Ingress and environment networking               |
| Security          | Services need Azure resources             | Managed identity and secrets                     |
| Operations        | Kubernetes complexity                     | Azure-managed orchestration layer                |

### **B4. WHAT exactly is Azure Container Apps?**

**Simple definition**

Azure Container Apps is a service where you deploy Docker containers and Azure manages much of the infrastructure and orchestration required to run them.

**Technical definition**

Azure Container Apps is a managed application platform built on Kubernetes technologies. It uses an environment, revisions, replicas, ingress, workload profiles and KEDA-based scaling to operate containerized workloads.

You do not manage the underlying Kubernetes cluster directly.

#### **Request path**

Suppose a user requests account details.

1. User sends HTTP request.
2. Request reaches the Container Apps ingress endpoint.
3. Ingress routes traffic to the appropriate Container App.
4. Container Apps directs traffic to an eligible replica of the active revision.
5. Your ASP.NET Core API processes the request.
6. The API accesses its database or another service.
7. The response returns to the user.

### **B5. Revised 1-minute answer — v2**

Azure Container Apps is a managed platform for deploying and operating containerized applications. It allows us to run multiple independently managed services without directly managing a Kubernetes cluster.

For example, in a banking system, Customer API and Payment API can scale based on HTTP traffic, while a Notification Worker can scale based on Azure Service Bus queue messages through KEDA. A worker can scale to zero when there are no messages, if configured.

It also provides revisions, traffic splitting, ingress, managed identity, secrets, networking and workload profiles. We choose it when we need container-based workloads and flexible event-driven scaling without the operational overhead of managing AKS.

## **BLOCK C — Features and internal working**

This is the most important block for understanding Container Apps technically.

### **C1. Feature catalogue**

I'll classify the features by how important they are for a Principal .NET Engineer.

### **1. Container Apps Environment**

Fundamental

**Layman explanation:** Think of an environment as a common campus where you run multiple independent applications.

For example, you might have one environment containing:

- Customer API.
- Payment API.
- Notification Worker.
- Reporting Worker.

They can share environment-level networking and logging capabilities.

**Technical understanding:**

An environment is a secure boundary around one or more Container Apps and Container Apps Jobs. It provides shared networking and infrastructure management.

You can create an environment with a Microsoft-managed network or integrate it with your own Virtual Network, depending on the environment configuration.

**Why does this matter?**

Suppose your Payment API should communicate privately with your Customer API. You can configure internal ingress and use the environment's service discovery instead of exposing every service publicly.

**Important design decision:** Do not automatically put every application in one environment. Separate environments when you need meaningful isolation, different network boundaries, or different operational ownership.

### **2. Container App, Container and Replica**

Fundamental

These three terms are frequently confused.

Imagine your Payment API.

- Container App = the Payment API service as managed by Azure.
- Container = the actual running packaged application.
- Replica = one running instance of that application.

Example:

**Payment API — one Container App**

**Replica 1**

Payment container

**Replica 2**

Payment container

**Replica 3**

Payment container

Three replicas mean three running copies of the Payment API revision.

Why have replicas?

If one instance receives too many requests, the platform can add more instances. Traffic can then be distributed across the available replicas.

**Important:** A replica is not a new microservice. It is another running copy of the same Container App revision.

### **3. Ingress**

Fundamental

**Layman explanation:** Ingress is the entry gate to your application.

Imagine your bank has a building with four departments. Customers should not walk directly into every department. There is an entry gate that directs them to the correct place.

Ingress does something similar for network traffic.

For example:

- Customer API has an external endpoint for customers.
- Payment API is internal-only.
- Notification Worker has no HTTP ingress because it consumes queue messages.

Container Apps supports HTTP and TCP ingress.

Two common configurations:

| Type             | Meaning                                                             | Example             |
| ---------------- | ------------------------------------------------------------------- | ------------------- |
| External ingress | Reachable from outside the environment, subject to network controls | Public Customer API |
| Internal ingress | Reachable only through the internal environment/network path        | Private Payment API |

**Principal-level point:** Not every microservice should have a public endpoint. Expose only the required entry points and keep internal services private.

### **4. Revisions**

Important

**Layman explanation:** A revision is a version of your deployed application.

Suppose your Payment API is currently version 1.

You deploy a new version with a bug fix.

Container Apps creates a new revision, allowing you to manage the new version alongside the old version.

Example:

**Payment API**

**Revision 1**

Old version

# **90%**

Traffic

**Revision 2**

New version

# **10%**

Traffic

Illustrative traffic allocation, not an automatic default.

This is called traffic splitting.

You can:

- Send 10% of traffic to the new revision.
- Observe its performance.
- Increase it to 50%.
- Eventually move 100% of traffic to the new revision.
- Roll back traffic to the previous revision if problems occur.

This supports canary and blue/green deployment strategies.

**Two revision modes:**

- Single revision mode: the platform manages the transition between revisions, keeping the previous revision available until the new revision is ready.
- Multiple revision mode: you manage multiple active revisions and their traffic allocations.

**Failure scenario:** Your new Payment API has a defect. You notice increased errors after sending 10% of traffic to it. You can redirect traffic to the old revision while investigating.

**Important:** Revisions do not automatically make database schema changes backward-compatible. Your deployment must still handle old and new application versions safely.

### **5. Autoscaling and KEDA**

Fundamental

This is probably the most important feature for your understanding.

**Layman explanation:** Imagine a bank counter.

If 5 customers arrive, one employee may be enough.

If 500 customers arrive, the bank opens more counters.

Container Apps does something similar with replicas.

But the interesting part is that it can watch more than HTTP traffic.

#### **What can trigger scaling?**

| Scaling signal               | Simple example                            |
| ---------------------------- | ----------------------------------------- |
| HTTP requests                | API receives more customer requests       |
| Service Bus messages         | Queue has 1,000 pending messages          |
| Event Hubs                   | Event processing workload increases       |
| Kafka                        | More events are waiting                   |
| CPU                          | Application CPU usage increases           |
| Memory                       | Application memory usage increases        |
| Other KEDA-supported sources | Redis, Prometheus and other event sources |

Microsoft documents KEDA-based scaling for these event sources.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



#### **What is KEDA?**

KEDA stands for Kubernetes Event-driven Autoscaling.

In simple English:

**KEDA watches an external workload signal and tells the platform how many application replicas are needed.**

Consider your Notification Worker.

**Azure Service Bus Queue**

# **1,000**

Waiting messages — example

KEDA observes queue length

**Notification Worker**

R1

R2

R3

R4

Illustrative: four replicas processing messages

When messages increase, the configured scaling rule can cause more replicas to start.

When the queue becomes empty, replicas can scale down, potentially to zero.

**Important distinction:**

- KEDA does not process your messages.
- Your .NET worker processes messages.
- KEDA observes the queue and influences the replica count.

#### **Scale-to-zero**

Suppose your Notification Worker has no messages for an hour.

Instead of keeping a worker running all the time, you can configure:

- Minimum replicas = 0.
- Maximum replicas = 10.
- A Service Bus scaling rule.

When there is no work, the worker can scale to zero.

When messages arrive, it can start again.

Production caution

Scale-to-zero can introduce startup delay. If a payment-related consumer must react immediately, you may choose minimum replicas of 1 or more.

Also, CPU- and memory-based scaling alone cannot scale an app to zero.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



#### **What happens when the worker scales out?**

Suppose 4 replicas start.

All four may attempt to consume messages from the same Service Bus queue.

Your design must account for:

- Concurrent message processing.
- Duplicate delivery.
- Lock renewal and lock expiry.
- Idempotency.
- Poison messages and dead-letter queues.
- Database connection limits.

Scaling more replicas does not automatically make message processing safe.

### **6. Container Apps Jobs**

Important

**Layman explanation:** A normal Container App is like an employee who is available to keep working. A Job is like hiring someone to complete one specific task and leave.

Examples:

- Generate a monthly report.
- Process a large CSV file.
- Reconcile transactions.
- Import a bulk customer file.
- Run a scheduled cleanup.

Container Apps Jobs support three common execution patterns:

| Job type     | Example                                   |
| ------------ | ----------------------------------------- |
| Manual       | Start a reconciliation job when requested |
| Scheduled    | Generate reports every night              |
| Event-driven | Start executions when events arrive       |

**Difference between a worker and a job:**

- Worker: continuously listens for work and processes messages.
- Job: starts an execution, performs its task and completes.

For example, a Notification Worker can continuously consume messages, while a MonthlyReportJob starts at midnight, creates a report and exits.

### **7. Workload Profiles**

Important

**Layman explanation:** Different applications need different types of computers.

A reporting application may need a lot of memory. A small API may need very little.

Workload profiles determine the compute resources available to your Container Apps.

Current profile categories include:

| Profile     | Simple explanation                    | Suitable for                                    |
| ----------- | ------------------------------------- | ----------------------------------------------- |
| Consumption | Pay based on usage                    | Unpredictable or bursty workloads               |
| Dedicated   | Reserved compute pool                 | Steady workloads and resource isolation         |
| Flex        | Newer profile type, currently preview | Specific isolation and performance requirements |

The Flex profile is currently marked Preview in Microsoft's documentation. It has different billing and scaling characteristics, including no scale-to-zero.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn



**Principal-level decision:** Don't choose Consumption automatically for everything. Consider predictable traffic, isolation, resource requirements, cold-start tolerance and cost.

### **8. Dapr integration**

Advanced

Dapr means Distributed Application Runtime.

**Layman explanation:** Imagine every microservice needs to communicate with other services, publish messages, access state or handle secrets. Instead of implementing all the distributed-system plumbing yourself, Dapr provides reusable building blocks.

Examples:

- Service-to-service invocation.
- Publish/subscribe messaging.
- State management.
- Secrets integration.
- Distributed tracing support.

Dapr commonly runs as a sidecar alongside your application container.

**Customer API replica**

**.NET API**

Business logic

Distributed capabilities

**Important:** Dapr is optional. You do not need it just because you use Container Apps. If your architecture already uses direct HTTP and Azure Service Bus SDKs effectively, you may not need Dapr.

### **9. Managed Identity and Secrets**

Fundamental

Your Payment API needs to access Azure SQL or Key Vault.

A common beginner approach is to store a username and password in configuration.

That creates a security risk.

With managed identity:

1. Azure assigns an identity to your Container App.
2. Your .NET application requests an access token.
3. Azure validates the identity.
4. The application receives access based on its assigned permissions.

Example:

```
using Azure.Identity;
using Azure.Security.KeyVault.Secrets;

var credential = new DefaultAzureCredential();

var client = new SecretClient(
    new Uri("https://my-vault.vault.azure.net/"),
    credential);

KeyVaultSecret secret =
    await client.GetSecretAsync("DatabasePassword");
```

In production, prefer managed identity and passwordless authentication where supported, rather than retrieving long-lived credentials unnecessarily.

**Secrets in Container Apps:**

You can define secrets and reference them from environment variables or mounted files. A secret is not automatically a secure database credential rotation strategy; plan how applications refresh values when secrets change.

### **10. Networking**

Important

Container Apps environments support Virtual Network integration.

Your services might need to communicate with:

- Azure SQL.
- Azure Key Vault.
- Service Bus.
- Internal APIs.
- On-premises banking systems.

You must design ingress, outbound connectivity, private endpoints, DNS, routing and firewall rules appropriately.

Internal ingress is not a substitute for authorization. A private service must still authenticate and authorize callers.

### **11. Monitoring and observability**

Fundamental

You should monitor:

- Request rate.
- Response time.
- HTTP error rate.
- Replica count.
- CPU and memory.
- Container restarts.
- Failed deployments.
- Queue length and message age.
- Dead-letter messages.

Use:

- Azure Monitor.
- Log Analytics.
- Application Insights.
- Structured .NET logging.
- Distributed tracing and correlation IDs.

For your .NET background workers, ensure every message has a correlation identifier that follows it through processing.

### **C2. Execution internals — what happens behind the scenes?**

Now let's move from what the features do to what happens at runtime.

#### **1. How does a Container App start?**

Imagine you deploy a new version of your .NET Payment API.

The flow is:

1. **You deploy a container image**

   The image is stored in Azure Container Registry or another supported registry.
2. **Container Apps receives the deployment configuration**

   It knows the image, CPU, memory, environment variables, secrets and scaling configuration.
3. **A revision is created**

   The revision represents the deployed application configuration.
4. **The platform starts replicas**

   The required containers are started using the configured compute resources.
5. **Health and readiness are evaluated**

   Configured probes help determine whether the container is alive and ready to receive traffic.
6. **Traffic is routed**

   Ingress and revision traffic allocation determine where requests go.

You don't manually create Kubernetes Deployments, ReplicaSets or Pods for the normal Container Apps workflow.

#### **2. What happens when scaling is required?**

Suppose your Notification Worker has a Service Bus scaling rule.

1. KEDA observes the configured event source.
2. It evaluates the scaling rule and its target.
3. The scaling system determines the desired replica count.
4. Container Apps starts or stops replicas.
5. Each new replica starts your .NET worker.
6. The worker connects to Service Bus and processes messages.

The desired replica count is a target, not a guarantee that every replica starts immediately. Capacity, startup time and platform conditions matter.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



#### **3. What happens inside a replica?**

Your .NET process runs inside the container.

For example:

```
Container Apps replica
    |
    +-- .NET 8 Worker Process
           |
           +-- ServiceBusProcessor
           |
           +-- Message Handler
           |
           +-- Business Logic
           |
           +-- Database Repository
```

Important: Container Apps scales replicas, not the number of threads inside your .NET application.

Your application must still implement concurrency correctly.

For example, if four replicas each process ten messages concurrently, you could have approximately 40 concurrent message handlers. That is an application-level concurrency decision, not a guaranteed platform setting.

#### **4. Memory and state**

A container replica can be stopped, restarted or replaced.

Therefore:

- Do not store important business state only in local memory.
- Do not assume a replica will remain alive forever.
- Store durable state in databases or other persistent services.
- Make message processing idempotent.
- Use distributed state only when there is a real requirement.

**Principal-level lesson:** Container Apps provides infrastructure scaling. It does not make your application stateless, thread-safe or fault-tolerant automatically.

#### **5. Networking and service discovery**

Suppose Payment API calls Customer API.

You can use internal service-to-service HTTP communication through the environment's internal DNS-based service discovery.

You can also communicate through messaging:

```
Payment API
     |
     | Publish PaymentCompleted
     v
Azure Service Bus
     |
     v
Notification Worker
```

Use synchronous HTTP when the caller needs an immediate response. Use messaging when the work can happen asynchronously or should be decoupled.

## **BLOCK D — Decisions and trade-offs**

### **D1. Comparison matrix: App Service vs Container Apps vs AKS**

This is the comparison you should remember for interviews.

| Dimension                   | App Service                            | Container Apps                        | AKS                                                      |
| --------------------------- | -------------------------------------- | ------------------------------------- | -------------------------------------------------------- |
| Primary purpose             | Managed web/API hosting                | Managed container workloads           | Managed Kubernetes                                       |
| Container support           | Yes                                    | Yes                                   | Yes                                                      |
| Multiple applications       | Yes                                    | Yes                                   | Yes                                                      |
| HTTP scaling                | Yes                                    | Yes                                   | Yes, with configured autoscaling                         |
| Queue/event scaling         | Requires additional design/integration | Built-in KEDA-based scaling           | Possible through KEDA/configuration                      |
| Scale to zero               | Not typical for App Service web apps   | Supported for eligible configurations | Possible with additional components and design           |
| Background workers          | WebJobs or containers                  | First-class container workloads       | First-class container workloads                          |
| Revisions/traffic splitting | Deployment slots                       | Native revisions and traffic weights  | Kubernetes deployment/service/ingress tooling            |
| Kubernetes control          | No                                     | No direct cluster control             | Yes                                                      |
| Operational overhead        | Low                                    | Low to medium                         | Highest                                                  |
| Team skills                 | App Service and Azure                  | Containers and Azure                  | Kubernetes expertise                                     |
| Exit cost                   | Application hosting migration          | Container platform migration          | Kubernetes portability, with cloud-specific dependencies |
| Typical choice              | Web application/API                    | APIs, event workers, microservices    | Complex platform requiring Kubernetes control            |

**Cost:** There is no universally cheapest option. App Service uses plan-based pricing; Container Apps has consumption and dedicated billing models; AKS has cluster-management and underlying infrastructure costs. Compare the actual deployment shape and expected utilization rather than just the service names.

**Regulatory impact:** None of these services automatically makes a banking workload compliant. Network isolation, identity, encryption, logging, data residency, audit and governance must be designed.

### **D2. Trade-offs — what do you gain and sacrifice?**

**What you gain with Container Apps**

- You can deploy containerized services without managing a Kubernetes cluster.
- Different workloads can scale independently.
- Background consumers can scale based on queue messages.
- Idle workloads can scale to zero in supported configurations.
- Revisions and traffic splitting simplify controlled deployments.
- Jobs support finite tasks.

**What you sacrifice**

- You don't get the same low-level Kubernetes control as AKS.
- Scale-to-zero introduces cold-start considerations.
- The application still needs production-grade retry, idempotency and observability.
- You must understand container images, networking, compute limits and scaling rules.
- Some advanced platform requirements may require AKS or another service.

### **D3. When should you use or avoid Container Apps?**

**Use it when:**

- You have multiple containerized APIs and workers.
- Different services need different scaling signals.
- You have queue consumers that should scale with queue length.
- You need scheduled or event-driven container jobs.
- You want revisions and traffic splitting without managing AKS.

**Avoid it or evaluate alternatives when:**

- You only have a straightforward website or REST API: App Service may be simpler.
- You need deep Kubernetes control, custom operators or extensive cluster-level customization: evaluate AKS.
- Your workload requires very predictable immediate response and cannot tolerate cold starts: configure minimum replicas or evaluate another hosting option.
- You need a simple event-triggered function rather than a long-running container workload: Azure Functions may be more appropriate.

**Prerequisites:**

- Container image and registry knowledge.
- Basic Docker and container debugging.
- HTTP, DNS and networking fundamentals.
- Understanding of Azure identity and secrets.
- Understanding of concurrency, retries and idempotency.
- Monitoring and operational ownership.

### **D4. What would change my mind?**

Suppose I initially recommend Container Apps for your banking microservices.

I would reconsider if:

1. All services are straightforward HTTP APIs with stable traffic and the team already operates App Service well.
2. The organization needs Kubernetes operators, custom networking or cluster-level control.
3. The workload has strict latency requirements and scale-to-zero startup is unacceptable.
4. The cost model shows a dedicated or App Service plan is more economical for the actual traffic.
5. Regulatory or platform policies require a different hosting boundary.

**Principal Engineer rule:** Choose the least complex platform that satisfies the workload's functional, operational, security and performance requirements.

## **BLOCK E — Implementation and operations**

### **E1. End-to-end .NET implementation**

Let's build a hypothetical .NET 8 Notification Worker that consumes messages from Azure Service Bus.

We will use:

- .NET 8 Worker Service.
- Docker.
- Azure Container Registry.
- Azure Container Apps.
- Azure Service Bus.
- Managed identity where supported.
- KEDA-based scaling.

#### **Step 1: Create the worker project**

```
dotnet new worker -n NotificationWorker
cd NotificationWorker

dotnet add package Azure.Messaging.ServiceBus
dotnet add package Azure.Identity
```

#### **Step 2: Write the worker**

For clarity, this example uses a Service Bus connection string loaded from configuration. In production, prefer managed identity authentication.

`Program.cs`:

```
using Azure.Messaging.ServiceBus;
using Microsoft.Extensions.Hosting;

var builder = Host.CreateApplicationBuilder(args);

var connectionString =
    builder.Configuration["ServiceBus:ConnectionString"];

var queueName =
    builder.Configuration["ServiceBus:QueueName"];

if (string.IsNullOrWhiteSpace(connectionString) ||
    string.IsNullOrWhiteSpace(queueName))
{
    throw new InvalidOperationException(
        "Service Bus configuration is missing.");
}

builder.Services.AddSingleton(_ =>
    new ServiceBusClient(connectionString));

builder.Services.AddHostedService<NotificationWorker>();

await builder.Build().RunAsync();
```

`NotificationWorker.cs`:

```
using Azure.Messaging.ServiceBus;
using Microsoft.Extensions.Hosting;
using Microsoft.Extensions.Logging;

public sealed class NotificationWorker : BackgroundService
{
    private readonly ServiceBusClient _client;
    private readonly ILogger<NotificationWorker> _logger;
    private ServiceBusProcessor? _processor;

    public NotificationWorker(
        ServiceBusClient client,
        ILogger<NotificationWorker> logger)
    {
        _client = client;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        _processor = _client.CreateProcessor(
            "notifications",
            new ServiceBusProcessorOptions
            {
                MaxConcurrentCalls = 5,
                AutoCompleteMessages = false
            });

        _processor.ProcessMessageAsync += async args =>
        {
            try
            {
                string body = args.Message.Body.ToString();

                _logger.LogInformation(
                    "Processing notification {MessageId}",
                    args.Message.MessageId);

                // TODO: Invoke notification business logic.
                // Make processing idempotent.

                await args.CompleteMessageAsync(args.Message);
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Notification processing failed");

                // Let Service Bus retry according to its
                // delivery and lock configuration.
                throw;
            }
        };

        _processor.ProcessErrorAsync += args =>
        {
            _logger.LogError(
                args.Exception,
                "Service Bus processor error");

            return Task.CompletedTask;
        };

        await _processor.StartProcessingAsync(stoppingToken);

        try
        {
            await Task.Delay(
                Timeout.Infinite,
                stoppingToken);
        }
        catch (OperationCanceledException)
        {
            // Normal shutdown.
        }

        await _processor.StopProcessingAsync();
    }

    public override async Task StopAsync(
        CancellationToken cancellationToken)
    {
        if (_processor is not null)
        {
            await _processor.DisposeAsync();
        }

        await base.StopAsync(cancellationToken);
    }
}
```

This is a teaching skeleton, not production-ready payment or notification processing. A production handler needs proper exception classification, duplicate detection/idempotency, dead-letter handling, graceful shutdown, telemetry and explicit retry policy.

### **E3. Production readiness and SLO/SLI**

Your release checklist:

- Image is built reproducibly and scanned.
- ACR authentication uses managed identity.
- Secrets are stored securely, preferably in Key Vault.
- Managed identities have least-privilege permissions.
- Internal services are not unnecessarily exposed publicly.
- CPU, memory and replica limits are configured.
- Minimum and maximum replicas are appropriate.
- Queue processing is idempotent.
- Dead-letter handling is implemented.
- Health probes are configured appropriately.
- Graceful shutdown is supported.
- Logs, metrics and traces are available.
- Alerts and dashboards are configured.
- Revision rollback has been tested.
- Database capacity has been tested under peak replica count.
- Disaster recovery and backup strategy is documented.

**SLI:** What you measure.

- API availability.
- API latency.
- Queue processing delay.
- Message failure rate.
- Successful job completion.

**SLO:** What you promise internally.

Example targets, purely illustrative:

- API availability: 99.9%.
- 95th percentile API latency: below 500 ms.
- 99% of notification messages processed within 2 minutes.

**Error budget:** If the service has a 99.9% monthly availability target, the permitted unavailability is approximately 0.1% of the month. Use the budget to decide whether to prioritize reliability work over new releases.

#### **Example: Payment processing**

1. Customer submits a payment request.
2. Payment API authenticates and validates it.
3. Payment API writes the transaction to its database.
4. Payment API records an event in an Outbox table within the same transaction.
5. An Outbox publisher publishes the event to Service Bus.
6. Notification Worker receives the event.
7. KEDA scales the Notification Worker based on queue demand.
8. The worker sends the notification.
9. The worker records completion using an idempotency key.

**Why this design?**

The Payment API should not wait for an SMS or email to finish before responding to a successful payment. Notification is an asynchronous business process.

Container Apps helps operate the worker independently. The Outbox pattern, idempotency and transaction handling are application architecture responsibilities—not features automatically provided by Container Apps.

### **F2. Principal/Architect perspective**

When you propose Container Apps in an architecture review, don't say:

"Container Apps is better because it supports microservices."

That is not a sufficient technical justification.

Instead, explain:

1. What workloads are being hosted?
2. What are their scaling patterns?
3. Which services need event-driven scaling?
4. What is the cold-start tolerance?
5. What are the networking and security requirements?
6. What is the expected utilization and cost?
7. What operational responsibilities does the team want to own?
8. Why does App Service or AKS not provide a better fit?

#### **Trade-off defence template**

**Decision:** Use Azure Container Apps.

**Business requirement:** Independent API and background processing workloads.

**Technical reason:** Queue-driven scaling, scale-to-zero for eligible workers, revisions and managed container hosting.

**Alternative considered:** App Service and AKS.

**Why not App Service?** It can host the applications, but the required queue-driven container scaling and worker lifecycle are more naturally handled through Container Apps.

**Why not AKS?** The team does not require direct Kubernetes control, operators or cluster-level customization.

**Risk:** Cold starts, message duplication, database saturation and platform dependency.

**Mitigation:** Minimum replicas where needed, idempotent handlers, concurrency controls, monitoring and tested rollback.

### **F3. Misconceptions and anti-patterns**

| Misconception                                     | Correct understanding                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Container Apps is just Docker hosting             | It includes orchestration, scaling, revisions and ingress                       |
| Every microservice needs Container Apps           | App Service and other compute options can host microservices                    |
| Container Apps means no Kubernetes anywhere       | It is built on Kubernetes technology, but you don't directly manage the cluster |
| KEDA processes queue messages                     | Your application processes messages; KEDA drives scaling                        |
| Scale to zero means no delay                      | Starting a new replica takes time                                               |
| More replicas always mean more throughput         | Database and downstream systems may become bottlenecks                          |
| Revisions make database rollback safe             | Database compatibility must be designed separately                              |
| Managed identity removes all secrets              | Some external services still require credentials                                |
| Dapr is mandatory                                 | Dapr is optional                                                                |
| Container Apps guarantees exactly-once processing | Your distributed application must handle duplicates and retries                 |

**Particularly dangerous anti-patterns:**

- Storing payment state in local memory.
- Allowing unlimited message concurrency.
- Scaling a worker to 100 replicas without checking database capacity.
- Exposing internal services publicly.
- Putting secrets in Docker images.
- Using a single shared managed identity with excessive permissions.
- Treating every failed message as a reason to retry forever.

### **F4. Migration and evolution**

#### **App Service to Container Apps**

Imagine you currently have a .NET 8 API in App Service.

A sensible migration path:

1. Identify application dependencies.
2. Containerize the .NET application.
3. Test the image locally.
4. Push it to ACR.
5. Create a Container Apps environment.
6. Configure identity, ingress, networking and secrets.
7. Deploy the API as a Container App.
8. Validate health checks, logs and scaling.
9. Send a small percentage of traffic to the new endpoint through your traffic-management layer.
10. Shift traffic gradually and retain a rollback path.

**Important:** An App Service deployment slot does not simply become a Container Apps revision. The deployment and networking architecture must be adapted.

#### **AKS to Container Apps**

Consider migration when:

- You use only a subset of Kubernetes features.
- You do not need cluster-level customization.
- Your workload fits Container Apps' supported runtime model.
- Reducing operational overhead is a priority.

Do not migrate if your system depends heavily on custom Kubernetes operators, cluster-level policies, specialized scheduling or unsupported integrations.

### **F5. Cost and operational overhead**

Let's understand cost without inventing Azure prices.

#### **Consumption profile**

You pay according to the consumption model, which considers:

- vCPU usage.
- Memory usage.
- Requests, where applicable.
- Free allowances and billing rules applicable to the selected region and configuration.

When eligible applications scale to zero, they do not incur replica usage charges for the period at zero. Other resources such as the environment, registry, databases and messaging services may still cost money.&#x20;

### **G2. Scenario-based interview answers**

#### **Scenario 1 — Happy path**

**Interviewer:** How would you deploy a .NET microservice to Container Apps?

**Answer:** I would package the .NET application into a Docker image, push it to ACR, configure a Container Apps environment, deploy the image as a Container App, and configure ingress, managed identity, health probes and scaling. I would monitor the revision and replicas through Azure Monitor and Application Insights.

**Follow-up:** How would you release a new version?

Use revisions and traffic splitting, validate the new version, and progressively move traffic.

**Trade-off:** This does not remove the need for backward-compatible database migrations.

#### **Scenario 2 — Failure and recovery**

**Interviewer:** Your Notification Worker crashes while processing a message. What happens?

**Answer:** The container may restart or a replica may be replaced. If the message has not been completed, Service Bus can redeliver it after the relevant lock and delivery rules apply. I would make the handler idempotent, configure retry and dead-letter handling, and monitor repeated failures.

**Follow-up:** How do you prevent duplicate SMS messages?

Use a durable idempotency record keyed by the business notification identifier, and ensure the sending workflow handles retries safely.

**Trade-off:** Exactly-once side effects cannot be assumed merely because the platform runs a worker.

#### **Scenario 3 — 10× scale**

**Interviewer:** Your Service Bus queue increases from 100 to 100,000 messages. What do you do?

**Answer:** I would configure KEDA-based scaling, define minimum and maximum replicas, tune the target queue depth and worker concurrency, and test end-to-end throughput. I would also check downstream database and provider limits.

**Follow-up:** Why not set maximum replicas to 1,000?

Because more replicas may overwhelm the database, external provider or message lock configuration. Scaling limits must be based on measured capacity.

**Trade-off:** Faster draining of the queue versus increased resource and downstream costs.

#### **Scenario 4 — Security**

**Interviewer:** How does your Payment API connect securely to Azure SQL?

**Answer:** I would use managed identity and Microsoft Entra authentication, assign the minimum required database permissions, and use private networking where required. I would avoid embedding passwords in the image or source code.

**Follow-up:** Would you expose Payment API publicly?

Only if there is a genuine external access requirement. Otherwise, use internal ingress and a controlled API gateway or service communication path.

**Trade-off:** More secure boundaries require thoughtful DNS, routing and troubleshooting.

#### **Scenario 5 — Cost**

**Interviewer:** How do you reduce cost for a low-volume worker?

**Answer:** I would consider Consumption workload profiles, minimum replicas of zero and KEDA event-driven scaling. I would measure cold-start tolerance and total downstream costs before deciding.

**Follow-up:** What if the first notification must be sent within one second?

I would evaluate keeping one or more replicas warm, reducing startup work and testing end-to-end latency.

**Trade-off:** Lower idle compute cost versus faster startup and response time.

#### **Scenario 6 — Migration**

**Interviewer:** Why migrate from App Service to Container Apps?

**Answer:** I would not migrate solely to adopt a newer service. I would migrate if the application requires container-native workload management, queue-based autoscaling, scale-to-zero for background processing, or revision-based traffic management that better fits the architecture.

**Follow-up:** Can App Service already run containers?

Yes. Container support is not the reason by itself. The workload's scaling and operational requirements determine the decision.

**Trade-off:** Better fit for event-driven workloads versus migration effort and platform-specific dependencies.

#### **Scenario 7 — Monitoring and incident**

**Interviewer:** Your API latency increases after a deployment. How do you investigate?

**Answer:** I would compare telemetry across revisions, inspect request and dependency duration, review replica count, CPU and memory, and check downstream database latency. If the new revision is responsible, I would shift traffic back to the previous healthy revision.

**Follow-up:** What if both revisions are slow?

Investigate shared dependencies, network, resource saturation and platform-wide conditions.

**Trade-off:** Rollback restores service quickly but does not explain the root cause.

#### **Scenario 8 — Alternatives**

**Interviewer:** Why not AKS?

**Answer:** AKS is preferable when we need direct Kubernetes control, operators, custom scheduling or complex platform capabilities. If the workload mainly needs managed container hosting, KEDA scaling, ingress and revisions, Container Apps can meet the requirement with less cluster operational overhead.

**Follow-up:** Can we move from Container Apps to AKS later?

Yes, but plan for differences in networking, deployment, observability, identity and Kubernetes-specific configurations.

**Trade-off:** Less operational complexity versus less infrastructure control.

#### **Scenario 9 — Enterprise and multi-team**

**Interviewer:** How would you organize 30 microservices across several teams?

**Answer:** I would establish environment boundaries based on security, networking and ownership requirements. I would standardize CI/CD, identity, observability, tagging, deployment policies and scaling templates. Teams would own their service configurations within those platform guardrails.

**Follow-up:** Would you create one environment per microservice?

Not automatically. That can add operational complexity. I would group services according to actual isolation and networking requirements.

**Trade-off:** Shared environments improve reuse, while separate environments provide stronger isolation.

#### **Scenario 10 — Business case**

**Interviewer:** How do you justify Container Apps to management?

**Answer:** I would show the operational cost of running and maintaining Kubernetes, the development and deployment requirements, expected utilization, scaling patterns and projected cost. I would compare it with App Service and AKS using actual workload measurements.

**Follow-up:** Is Container Apps always cheaper?

No. It depends on utilization, profile choice, replicas, supporting services and operational costs.

**Trade-off:** Reduced platform-management burden versus usage charges and service-specific limitations.

### **G5. Final self-test — 12 questions with answers**

**Q1. Can one Container Apps environment contain multiple Container Apps?**

Yes. An environment is a shared boundary for multiple apps and jobs.

**Q2. Does one Container App always have one replica?**

No. It can have zero or multiple replicas, depending on its configuration and scaling state.

**Q3. Does a new revision automatically mean all traffic moves to it?**

Not necessarily. Traffic behavior depends on the revision mode and traffic allocation configuration.

**Q4. Can a worker scale based on Kafka events?**

Yes, using an appropriate KEDA-supported scaler.

**Q5. Does KEDA process messages?**

No. It observes event-source metrics and influences scaling. Your application processes messages.

**Q6. What is the difference between a Container App and a Job?**

An app is generally a long-running workload. A job runs a finite task and completes.

**Q7. What happens if a worker scales to zero and a message arrives?**

The scaler detects the event and the platform can start a replica. Processing begins after startup, so there can be delay.

**Q8. Should every microservice have external ingress?**

No. Keep internal services private unless external access is required.

**Q9. Why use managed identity?**

To access supported Azure resources without storing long-lived credentials in application configuration.

**Q10. Can Container Apps replace AKS completely?**

No. AKS is more appropriate when direct Kubernetes control and advanced cluster-level capabilities are required.

**Q11. Why can more replicas reduce reliability?**

They can overwhelm shared dependencies such as SQL databases, caches or external APIs.

**Q12. What is the main reason to choose Container Apps over App Service?**

When the workload benefits from container-centric features such as KEDA event-driven scaling, queue-based background processing, scale-to-zero and revision traffic management—not simply because it uses containers.

### **Important correction: App Service can also scale from queue metrics**

Because this was the source of your earlier confusion, I want to correct an oversimplification from our earlier discussion.

**App Service is not limited to HTTP traffic.**

Azure Monitor autoscale can use metrics including CPU, memory, HTTP queue length and even Azure Service Bus queue length. However, its autoscale rules apply to the App Service Plan, so applications sharing that plan scale together. App Service automatic scaling based on HTTP traffic is a separate option with per-app settings on supported tiers.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+2



Container Apps provides KEDA-based scaling rules directly for individual container workloads, including event sources such as Service Bus, Kafka and Event Hubs. It also supports scale-to-zero for eligible configurations.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



This is a more accurate comparison:

| Requirement                                            | App Service                                        | Container Apps               |
| ------------------------------------------------------ | -------------------------------------------------- | ---------------------------- |
| Scale based on HTTP traffic                            | Yes                                                | Yes                          |
| Scale based on CPU/memory                              | Yes                                                | Yes                          |
| Scale based on Service Bus queue metrics               | Yes, through Azure Monitor autoscale configuration | Yes, through KEDA            |
| Independently configure scaling per container workload | Requires appropriate plan/app arrangement          | Native per-app scaling rules |
| Scale eligible background workload to zero             | Not typical for App Service plans                  | Yes                          |
| Native container workload jobs                         | Not its primary model                              | Yes                          |

**This is the real distinction:** Container Apps makes independently managed, event-driven container workloads a first-class hosting model. It is not that App Service cannot scale using queue metrics.

**Azure Container Apps**

A managed container-workload platform. Particularly useful when independently running and scaling APIs, background workers and event-driven services.

**Azure Kubernetes Service**

A managed Kubernetes platform. Choose it when you need control over Kubernetes and its advanced capabilities.

**My recommendation for your learning:** Don't memorize that Container Apps is better than App Service. Remember the workload requirements that justify choosing it.
