# Topic 11 — ICMP, MTU, and Path MTU Discovery (PMTUD)



## The practical problem

Imagine your laptop communicates with a banking API:

```
Laptop
  │
  ▼
Office Router
  │
  ▼
Firewall
  │
  ▼
Internet
  │
  ▼
Banking API
```

Your application sends data across several network devices. Now consider these situations:

- **A destination server is unreachable.**
- **A router does not know where to forward a packet.**
- **A packet's TTL reaches zero.**
- **A packet is too large for a network link.**
- **A VPN reduces the maximum packet size available for application traffic.**
- **A firewall blocks a particular type of network diagnostic message.**

**How does the sender learn what went wrong? How does it know whether a packet is too large?**

**ICMP helps with network diagnostics and error reporting. MTU and PMTUD help with packet-size constraints.**

### The "2 MB POST fails" incident

The classic production signature:

```
✅ POST /api/orders with 2 KB body   → 200 OK
❌ POST /api/orders with 2 MB body   → timeout
```

Ping works. TCP connect works. Small requests work. **Only large requests fail.**

**The cause:** somewhere on the path, a link has a smaller MTU than the sender's interface. The large packet is dropped by that link. The router tries to send **ICMP Fragmentation Needed** back to the sender — but **a firewall blocks ICMP.** The sender never learns. It retransmits the same oversized packet. **Repeated until timeout.**

**This is an MTU black hole.** And it's one of the most misdiagnosed problems in production.

### The 1980s internet crisis

By 1988, the internet was **fragmenting itself to death**. Routers were fragmenting large packets to fit smaller links, but reassembly was expensive and lossy. **One lost fragment = whole datagram discarded.** Congestion collapsed.

**The fix:** **Path MTU Discovery (RFC 1191)** — senders set the Don't Fragment bit, and routers report the next-hop MTU in ICMP Fragmentation Needed. Senders shrink to fit. **No more router fragmentation.**

**ICMP, MTU, and PMTUD exist because IP alone cannot signal failure, packets have size limits, and the internet needs a way to negotiate that size without fragmentation.**

## 1. WHY — Why were ICMP and MTU required?

Consider a basic network with two computers connected through routers.

**Without a standardized network error-reporting mechanism**, a sender has limited information when a packet fails:

```
Client --------------------> Router A
                                  │
                                  X
                             No valid route
```

**The client might simply wait for a response that never arrives.**

Similarly, if a packet was too large for an intermediate network link, the sender needed a way to discover that limitation.

Some network technologies could fragment packets — **but fragmentation introduced additional complexity and performance costs.**

### The three requirements

**ICMP — why IP needed a control protocol**

**IP forwards packets. But it cannot report errors.** The IP header has no mechanism to say:

- "Destination unreachable" (no route).
- "TTL expired" (routing loop).
- "Packet too big" (MTU).
- "Parameter problem" (bad header).

**Without feedback, senders would only know that delivery failed — eventually, via timeout.** Every failure would look like a network hang. **Impossible to diagnose.**

**ICMP (RFC 792, 1981) is IP's companion protocol** — the messages that report errors and enable diagnostics. It's **not a transport protocol** (no ports, no connections), but it runs **above IP** in the sense that ICMP messages are carried in IP packets.

**MTU — why links have size limits**

Every link has a **Maximum Transmission Unit** — the largest frame it can carry. This is a **physical and protocol constraint**:

- **Buffer memory** — routers have finite buffer per frame.
- **Latency** — a large frame occupies a link longer; smaller frames reduce latency.
- **Error detection** — smaller frames mean less data lost on corruption.
- **Standardization** — Ethernet's 1500 was a design choice; everything interoperates around it.

**Without MTU enforcement**, a router would either buffer indefinitely (memory exhaustion) or truncate packets (data loss). **Both are unacceptable.**

**PMTUD — why discovery was needed**

**Before PMTUD (before 1988), routers fragmented.** Large packets were split into smaller fragments at each hop with a smaller MTU, then reassembled at the destination.

**The fragmentation approach failed** for three reasons:

1. **CPU cost** — fragmenting every packet is expensive.
2. **Loss amplification** — losing one fragment forces retransmission of the whole original datagram.
3. **Congestion collapse** — retransmissions amplified the load, driving the 1988 internet crisis.

**PMTUD (RFC 1191)** — senders set the **DF (Don't Fragment) bit**. When a router encounters a packet larger than the next-hop MTU, it **drops the packet** and sends **ICMP Fragmentation Needed** (Type 3, Code 4) **with the next-hop MTU** in the ICMP header. The sender **shrinks the packet** and retries.

**IPv6 made PMTUD mandatory** (RFC 8200) — IPv6 routers **never** fragment (only senders do, and only if PMTUD fails). This makes PMTUD's correctness **critical** for IPv6.

### Analogy — the postal system with size limits

| Real-world | Network |
|---|---|
| Letterbox has a maximum slot size | Link has an MTU |
| You mail a large package | You send a large packet |
| Post office says "too big for this route" | Router sends ICMP Fragmentation Needed |
| You split the package or use a smaller envelope | You reduce packet size (PMTUD) |
| **Post office silently drops** it and never tells you | **ICMP blocked — MTU black hole** |

**ICMP is the postal notice that says "that didn't fit." PMTUD is the mechanism to use the right envelope after the notice.**

## 2. BEFORE — What existed before these mechanisms?

### A. Before ICMP — silent failures

The earliest IP (pre-RFC 792) had no control protocol. Errors were:

- **Silent drops** — the sender never learned why.
- **Application-level timeouts** — every failure looked like a hang.
- **Manual path probing** — admins had to trace manually.

**There was no way to diagnose** why a packet didn't arrive. Every problem looked the same.

### B. Before MTU standardization — per-link chaos

Before Ethernet's 1500-byte standard (1980), each network technology had its own maximum:

- **ARPANET IMP:** 1008 bytes.
- **IBM SNA:** 512 bytes.
- **X.25:** 128 bytes (later 4096).

**Cross-network communication required translation** — a packet that fit in one network didn't fit in another. **Gateways** had to fragment and reassemble, which was fragile.

**Ethernet's 1500 became the de facto standard** because Ethernet dominated; interop with the internet required common size.

### C. Before PMTUD — router fragmentation

Routers fragmented packets to fit smaller links:

```
Sender → [Router A] → [Router B] → [Router C] → Receiver
          (1500)     (1280)       (9000)

Router A receives 1500-byte packet, next link is 1280:
  → Fragments into 1280 + 220
Router B receives 1280 (fits) and 220 (fits):
  → Passes both through
Receiver reassembles:
  → 1280 + 220 = 1500
```

**Strengths:** transparent; worked without sender cooperation.

**Weaknesses:**
- **CPU cost** — every router that fragments pays for it.
- **Loss amplification** — losing one fragment loses the whole datagram.
- **Reassembly buffers** — the destination must hold incomplete datagrams until fragments arrive or time out (typically 30 seconds).
- **Congestion collapse** — retransmissions amplified the load (1988 crisis).

### What we needed

- **A standardized way to report network errors.**
- **A way to test reachability.**
- **A mechanism to discover the maximum packet size supported across a path.**

**ICMP + PMTUD provided all three.** Fragmenting at routers became the fallback (IPv4 only).

---

## 3. PROBLEM — Why was the previous approach insufficient?

There are four important problems.

### Problem A — No useful diagnostic feedback

An application timeout doesn't tell us whether:

- DNS failed.
- Routing failed.
- A firewall blocked traffic.
- The server was down.
- A network device dropped a packet.

**Without ICMP, every failure becomes a timeout.** Diagnosis is guesswork.

### Problem B — Different networks have different MTUs

One network link might support an MTU of 1500 bytes, while another supports only 1400.

**A packet that works on one link may not fit on another.** A single path traverses many MTUs.

### Problem C — Fragmentation overhead

If a packet is fragmented:

- The destination must reassemble the fragments.
- **If one fragment is lost, the original packet cannot be reassembled.**
- Senders retransmit the entire datagram — amplifying load.
- Routers spend CPU on fragmentation instead of forwarding.

**The 1988 congestion collapse** was directly caused by this.

### Problem D — Firewalls may block diagnostic messages

The sender might need an ICMP error to discover a network problem, but a firewall may block it.

**This can produce confusing symptoms:** small requests work, but large requests hang.

### The gap

We needed:

1. **A control protocol** — to report errors.
2. **A discovery mechanism** — to find the smallest MTU on a path.
3. **A way to avoid fragmentation** — with DF set, so routers don't fragment.
4. **Reliability of feedback** — ICMP must not be blocked, or PMTUD fails.

**ICMP + PMTUD provide all four.**

**The new vulnerability:** **ICMP blocking breaks PMTUD.** This is why MTU black holes exist — and why this topic is essential for production engineers.

## 4. WHAT — What is ICMP?

**ICMP stands for Internet Control Message Protocol.**

It is a **network-layer control and diagnostic protocol** used by hosts and routers to communicate information about IP delivery and network conditions.

**It is not a transport protocol like TCP or UDP.** ICMP is carried inside IP packets.

### Where ICMP fits

```
Application layer    HTTP / HTTPS / DNS
Transport layer      TCP / UDP
Internet layer       IP + ICMP      ← ICMP lives here
Link layer           Ethernet / Wi-Fi
```

A useful distinction:

- **TCP** carries application data reliably.
- **UDP** carries application datagrams.
- **ICMP** communicates network control and error information.

**ICMP itself does not use TCP or UDP ports.**

### IPv4 and IPv6

| Protocol | Associated control protocol |
|---|---|
| **IPv4** | ICMPv4 — IP protocol number **1** |
| **IPv6** | ICMPv6 — IPv6 next-header value **58** |

**ICMPv6 is particularly important** because IPv6 relies on it for functions such as Neighbor Discovery and Path MTU Discovery. **Blocking ICMPv6 breaks IPv6.**

### ICMP message types (IPv4)

| Type | Code | Name | Practical use |
|---|---|---|---|
| **0** | 0 | Echo Reply | `ping` response |
| **3** | 0 | Network Unreachable | Network troubleshooting |
| **3** | 1 | Host Unreachable | Host troubleshooting |
| **3** | 3 | Port Unreachable | UDP diagnostics |
| **3** | 4 | **Fragmentation Needed** | **PMTUD's key message** |
| **3** | 13 | Communication Administratively Prohibited | Firewall block |
| **4** | 0 | Source Quench | Congestion (deprecated) |
| **5** | 0/1/2/3 | Redirect | Better route exists |
| **8** | 0 | Echo Request | `ping` |
| **11** | 0 | Time Exceeded | `traceroute`'s key message |
| **11** | 1 | Fragment Reassembly Timeout | Reassembly failed |
| **12** | 0 | Parameter Problem | Bad header |

### ICMPv6 — much richer

ICMPv6 is **fundamental to IPv6 operation**, not just diagnostics:

| Type | Name | Purpose |
|---|---|---|
| **1** | Destination Unreachable | Error |
| **2** | **Packet Too Big** | **ICMPv6's PMTUD message** |
| **3** | Time Exceeded | TTL expired |
| **4** | Parameter Problem | Bad header |
| **128** | Echo Request | `ping` |
| **129** | Echo Reply | `ping` response |
| **133** | Router Solicitation | Host discovery of routers |
| **134** | **Router Advertisement** | **Delivers IPv6 default gateway** (Topic 10 gotcha) |
| **135** | Neighbor Solicitation | **IPv6's ARP equivalent** (Topic 12) |
| **136** | Neighbor Advertisement | Response to Neighbor Solicitation |
| **137** | Redirect | Better route |

**The critical distinction:** **ICMPv6 is not just diagnostics — it's essential for IPv6's operation.** Blocking ICMPv6 breaks IPv6 (no Neighbor Discovery, no Router Advertisement, no PMTUD).

### ICMP is often blocked — the production trap

**Security-conscious networks often block ICMP.** Reasons:

- **Reconnaissance** — `ping` and `traceroute` reveal network topology.
- **Amplification** — ICMP echo can be used for Smurf attacks (historical).
- **Some attacks** — ICMP redirects can hijack routes.

**But blanket ICMP blocking breaks:**

- **`ping`** — the most basic diagnostic.
- **`traceroute`** — path discovery.
- **PMTUD** — the Fragmentation Needed / Packet Too Big message is ICMP.
- **IPv6 operation** — Neighbor Discovery, Router Advertisement, etc.

**The Principal-level principle:**

> **Block ICMP selectively, not wholesale. Allow:**
> - **Echo Request/Reply** (for diagnostics — rate-limited).
> - **Fragmentation Needed / Packet Too Big** (for PMTUD — **critical**).
> - **Time Exceeded** (for traceroute).
> - **Destination Unreachable** (for diagnostics).
>
> **Block:**
> - **Redirect** (route hijacking risk — legitimate only on same L2).
> - **Source Quench** (deprecated).
> - **Echo to broadcast addresses** (Smurf mitigation).
> - **Oversized / malformed ICMP** (DoS mitigation).

## 5. FEATURES — What does ICMP provide?

| ICMP message | Meaning | Practical use |
|---|---|---|
| **Echo Request** | Request a response | `ping` |
| **Echo Reply** | Respond to echo request | `ping` result |
| **Destination Unreachable** | Packet cannot reach destination | Network troubleshooting |
| **Time Exceeded** | TTL or Hop Limit expired | `traceroute` |
| **Redirect** | Suggest a better next hop | Router guidance |
| **Fragmentation Needed** | IPv4 packet cannot be forwarded without fragmentation | PMTUD |

### Example 1 — Ping

```bash
ping google.com
```

Your system:

1. Resolves `google.com` using DNS.
2. Sends an ICMP Echo Request.
3. Waits for an ICMP Echo Reply.
4. Calculates round-trip time.

```
Reply from 142.250.x.x:
bytes=32 time=18ms TTL=116
```

**This indicates that an ICMP response was received.**

**Critical caveat:** **Successful ping does not prove that HTTPS or your .NET API is working.** A server may block ICMP while allowing TCP port 443.

### Example 2 — Destination Unreachable

A router that cannot forward a packet may send an ICMP Destination Unreachable message.

**This gives the sender diagnostic information rather than simply silently dropping the packet.**

However, some failures are intentionally dropped without an ICMP response (firewall rules, security policies).

### Example 3 — Time Exceeded

Every IPv4 packet has a **TTL (Time To Live)**. Every IPv6 packet has a **Hop Limit**.

A router decreases this value as it forwards the packet. When it reaches zero, the router discards the packet and **normally** sends an ICMP Time Exceeded message.

**This is how `traceroute` discovers network hops.**

### ICMP vs TCP vs UDP

| Dimension | ICMP | TCP | UDP |
|---|---|---|---|
| **Primary purpose** | Control and error reporting | Reliable data transport | Datagram transport |
| **Transport ports** | No | Yes | Yes |
| **Connection establishment** | No | Three-way handshake | No handshake |
| **Reliability** | No general delivery guarantee | Built-in reliability | No built-in reliability |
| **Common use** | Ping, errors, diagnostics | HTTPS, SQL, Kafka | DNS, real-time traffic |
| **Layer** | Network layer | Transport layer | Transport layer |

**Two common interview questions:**

> **Does ping use TCP?** No. Traditional ping uses ICMP Echo Request and Echo Reply messages.

> **Does ICMP guarantee packet delivery?** No. ICMP messages themselves may be lost or filtered.

## 6. COMPARISON — ICMP vs TCP vs UDP (10 dimensions)

| Dimension | ICMP | TCP | UDP |
|---|---|---|---|
| **Architecture** | Control/error reporting | Connection-oriented stream | Connectionless datagram |
| **Working mechanism** | Carried in IP packets, no ports | Handshake, ACKs, retransmission | Independent datagrams |
| **Performance** | Negligible overhead | Higher (handshake, ACKs) | Lower |
| **Scalability** | No per-connection state | Per-connection state | No per-connection state |
| **Reliability** | Best-effort delivery of ICMP messages | Built-in reliability | No built-in reliability |
| **Security** | Spoofable; often filtered | TLS over TCP | DTLS or custom |
| **Complexity** | Simple message types | Complex state machine | Simple |
| **Maintenance** | Simple policy | Well-understood | App must handle |
| **Cost** | None | CPU/memory | None |
| **Failure handling** | Reports errors but cannot prevent them | Retransmits, backs off | Silent loss |

## 7. ADVANTAGES AND DISADVANTAGES

### ICMP advantages
- **Explicit error feedback** — no more silent timeouts.
- **Diagnostics** — `ping`, `traceroute` built on ICMP.
- **PMTUD support** — the mechanism that makes PMTUD work.
- **IPv6 essential** — Neighbor Discovery, Router Advertisement.
- **Low overhead** — small messages, minimal impact.

### ICMP disadvantages
- **Best-effort** — ICMP messages can also be lost (no guarantee of delivery).
- **Not authenticated** — anyone can spoof ICMP messages (Smurf attacks, redirect attacks historically).
- **Frequently blocked** — breaks `ping`, `traceroute`, and **PMTUD**.
- **Misused for DoS** — historically Smurf, Fraggle attacks.
- **Asymmetric blocking** — the path may allow your packets but block ICMP replies.
- **Responses can be rate-limited** — high load may drop the Fragmentation Needed message.
- **ICMP errors don't always identify the root cause.**

### Principal Engineer lesson — never use ping as the only health check

**A ping is a reachability probe, not a health check.** A better health check tests the actual dependency and protocol you care about.

```powershell
Test-NetConnection trading-api.company.com -Port 443
```

**This tests TCP connectivity to port 443 — but still doesn't prove the application is healthy.** An HTTP health endpoint provides a more meaningful application-level check.

**The diagnostic ladder:**

| Test | What it proves |
|---|---|
| `ping` | IP reachability |
| `Test-NetConnection -Port` | TCP port open |
| `curl -v` | TLS + HTTP works |
| App health endpoint | Application is operational |

| ICMP type | Allow? | Reason |
|---|---|---|
| **Echo Request/Reply** | **Allow** (rate-limited) | Diagnostics; monitoring |
| **Destination Unreachable — Port** | **Allow** | UDP diagnostics |
| **Destination Unreachable — Fragmentation Needed** | **Allow** (critical) | PMTUD |
| **Destination Unreachable — Network/Host** | Allow | Diagnostics |
| **Time Exceeded** | **Allow** | `traceroute` |
| **Parameter Problem** | Allow | Diagnostics |

| **ICMPv6 — Neighbor Discovery, Router Advertisement** | **Allow** (essential) | IPv6 operation |
| **ICMPv6 — Packet Too Big** | **Allow** (critical) | PMTUD for IPv6 |

Suppose your .NET service calls `https://notification-api.internal` and reports a **timeout**.

2. Check the destination IP.
3. Check routing (Topic 9).
4. Check TCP 443 connectivity (Topic 7).
5. Investigate TLS negotiation (Topic 12).
6. Investigate HTTP response (Topic 21).
7. Check application logs and distributed traces (Topic 62).

**ICMP helps at the network layer, but it cannot replace application-level diagnostics.**

## 9. HOW — What is MTU?

**MTU stands for Maximum Transmission Unit.**

It is the **maximum size of a network-layer packet that can be carried in a single link-layer frame without fragmentation at that link.**

### Ethernet frame structure

```
┌─────────────────┬──────────────────────┬────────┐
│ Ethernet Header │ IP packet (payload)  │  FCS   │
│   14 bytes      │      1500 bytes      │ 4 bytes│
└─────────────────┴──────────────────────┴────────┘
```

**The typical Ethernet MTU is 1500 bytes.** That 1500-byte value refers to the **IP packet**, not the complete Ethernet frame.

### MTU vs MSS

An IPv4 packet contains:

- **IP header:** typically 20 bytes without options.
- **TCP header:** typically 20 bytes without options.
- **Application payload:** remaining space.

```
Ethernet MTU:       1500 bytes
- IPv4 header:       -20 bytes
- TCP header:        -20 bytes
─────────────────────────────────
TCP MSS (payload):   1460 bytes
```

**MSS = Maximum Segment Size** — the maximum TCP data payload a TCP endpoint is willing to receive in one segment.

**MTU and MSS are related but different:**
- **MTU** includes IP header + IP payload.
- **MSS** refers only to TCP data payload.

**For IPv4 Ethernet:**
```
MTU = 1500
IPv4 header = 20
TCP header = 20
MSS = 1460
```

**For IPv6 without extension headers:**
```
MTU = 1500
IPv6 header = 40
TCP header = 20
MSS = 1440
```

**For UDP:**
```
IPv4: 1500 - 20 - 8 = 1472 bytes max UDP payload
IPv6: 1500 - 40 - 8 = 1452 bytes max UDP payload
```

**Any UDP datagram > 1472** (IPv4) will be fragmented at the IP layer (or dropped if DF is set).

### Common MTUs

| Link type | MTU | Notes |
|---|---|---|
| **Ethernet (standard)** | 1500 | The internet default |
| **Ethernet with 802.1Q VLAN tag** | 1496 | The tag consumes 4 bytes |
| **PPPoE (DSL)** | 1492 | 8 bytes overhead |
| **PPTP VPN** | 1400 | 100 bytes overhead |
| **IPsec VPN (ESP)** | ~1400–1420 | Depends on cipher + mode |
| **GRE tunnel** | ~1476 | 24 bytes overhead |
| **WireGuard** | ~1420 | 80 bytes overhead |
| **VXLAN overlay** | ~1450 | 50+ bytes overhead |
| **Jumbo frames (datacenter)** | 9000 | Requires end-to-end support |

**The path MTU is the smallest MTU along the entire path.** A path with one 1400-MTU link has a path MTU of 1400.

### Why MTU matters — the path

```
Client
  │ MTU 1500
  ▼
Router A
  │ MTU 1400
  ▼
VPN Gateway
  │ MTU 1500
  ▼
Server
```

The smallest MTU along this path is **1400 bytes**. This is the **Path MTU**.

**A 1500-byte IP packet cannot be forwarded over the 1400-byte link without fragmentation or another mechanism to reduce packet size.**

## 10. INTERNAL WORKING — Fragmentation and PMTUD

### A. IPv4 fragmentation

Historically, IPv4 routers could fragment oversized packets when necessary, provided the packet's **Don't Fragment (DF) flag** was not set.

```
Original IPv4 packet = 3000 bytes
Next link MTU        = 1500 bytes

A router may divide the original packet into multiple fragments.
The destination reassembles them.
```

**Drawbacks:**

- Additional processing.
- More packets.
- **If one fragment is lost, the original packet cannot be fully reassembled.**
- Some firewalls and network devices handle fragments poorly.

### B. IPv4 Don't Fragment flag

IPv4 has a **DF (Don't Fragment) flag**.

**If DF is set, a router must not fragment that packet.**

If the packet is too large for the outgoing link, the router **drops it** and **should send an ICMP Destination Unreachable message with the fragmentation-needed indication (Type 3, Code 4)**.

**This information helps the sender reduce packet size.**

### C. Path MTU Discovery (PMTUD)

**PMTUD is a mechanism for discovering the smallest MTU along the entire path between two endpoints.**

- **IPv4 classic PMTUD** uses the DF flag and ICMP fragmentation-needed messages.
- **IPv6** routers do not fragment forwarded packets. They send ICMPv6 Packet Too Big messages, and the source adjusts its packet size.

**The flow:**

```
1. Client sends 1500-byte packet with DF set.

2. Router on path has MTU 1400.
   Packet is too large → dropped.

3. Router sends ICMP Fragmentation Needed (MTU 1400) to client.

4. Client caches path MTU = 1400.

5. Client retransmits at 1400 bytes (MSS reduced accordingly).

6. All subsequent packets fit.
```

### D. What is a Path MTU black hole?

This is a very important production failure.

**The scenario:**

- The path MTU is 1400.
- The sender sends 1500-byte packets with DF set.
- The router drops the oversized packets.
- The router sends an ICMP fragmentation-needed message.
- **A firewall blocks that ICMP message.**

**The sender never learns why the packets are being dropped.**

**The result:**

- TCP handshake succeeds (small packets fit).
- Small requests work.
- **Large requests hang.**
- TLS negotiation may fail or stall (large certs).
- The application reports timeouts.

**This is called a PMTU black hole.**

**The application may look unhealthy even though the real problem is the network path.**

### E. TCP MSS clamping

One workaround used by some routers and VPN gateways is **MSS clamping**.

The network device **adjusts the MSS value advertised during the TCP handshake** to fit the expected path MTU.

```
Normal IPv4 MSS: 1460
Adjusted MSS:    1360    ← forces sender to use smaller segments
```

**This can prevent oversized TCP segments on constrained paths.**

**However, MSS clamping is a TCP-specific workaround.** It does not solve all MTU problems, especially for **UDP traffic** (which has no MSS).

**The Principal-level rule:** **Fix PMTUD properly (allow the ICMP messages) rather than relying on MSS clamping.** But know MSS clamping exists — you'll meet it in the wild.

### F. TCP MTU probing (Linux kernel feature)

**`tcp_mtu_probing`** — a Linux kernel feature that **automatically discovers MTU** when PMTUD fails:

```bash
# 0 = disabled
# 1 = enabled on PMTUD black hole detection
# 2 = always enabled
sysctl -w net.ipv4.tcp_mtu_probing=1
```

**What it does:**

- **Detects MTU black holes** by observing repeated packet loss at the same size.
- **Probes smaller sizes** by setting different MSS values.
- **Adapts automatically** without requiring ICMP.

**This is a mitigation, not a fix.** The fix is always to allow ICMP. But `tcp_mtu_probing` is a useful safety net for systems behind flaky networks.

### G. IPv6 vs IPv4 fragmentation

| Aspect | IPv4 | IPv6 |
|---|---|---|
| **Router fragmentation** | Allowed | **Not allowed** |
| **Sender fragmentation** | Allowed (DF bit clear) | Allowed (sender-only) |
| **DF bit** | Explicit | **Implicit (always don't fragment)** |
| **PMTUD message** | ICMP Type 3 Code 4 | ICMPv6 Type 2 |
| **Dependency on PMTUD** | High | **Critical** (no router fallback) |

**The IPv6 change is fundamental.** In IPv4, if PMTUD fails (ICMP blocked), routers can still fragment. **In IPv6, they can't.** **MTU black holes are more severe in IPv6** — packets are dropped outright.

## 11. FAILURE SCENARIOS — Production troubleshooting

### Scenario 1 — Ping works but HTTPS fails

**Possible causes:**

- TCP 443 is blocked.
- TLS negotiation fails.
- The API is unavailable.
- DNS resolves to the wrong destination.
- Application firewall policy blocks traffic.

**Ping only tests ICMP Echo behavior. It does not prove TCP 443 or HTTPS works.**

### Scenario 2 — Small API requests work but large requests time out

**This is the classic MTU black hole signature.**

Investigate:

- Path MTU.
- ICMP filtering.
- VPN overhead.
- MSS negotiation.
- Firewall fragmentation handling.
- Packet loss.

**Diagnostic commands:**

```bash
# Find the largest payload that works
for size in 1000 1200 1400 1450 1472; do
    ping -M do -s $size -c 1 10.20.1.15 > /dev/null 2>&1 && echo "$size OK" || echo "$size FAIL"
done
```

**The largest size that works + 28 = path MTU.**

### Scenario 3 — Traceroute shows timeouts

**A timeout at one hop does not automatically mean that router is broken.**

Routers may:

- Filter ICMP.
- Rate-limit ICMP responses.
- **Forward packets normally while suppressing diagnostic responses.**

**Check whether subsequent hops and the final destination respond.**

### Scenario 4 — VPN traffic fails

VPN encapsulation adds extra headers:

```
Original packet
      │
      ▼
VPN encapsulation
      │
      ▼
Additional outer headers
      │
      ▼
Smaller effective inner packet size
```

**A 1500-byte packet may become too large after encapsulation.**

**This is why VPN networks often require MTU adjustment or MSS clamping.**

### Scenario 5 — Kubernetes overlay MTU

Some Kubernetes networking implementations use overlay networks such as **VXLAN**.

```
Original Pod packet
       │
       ▼
VXLAN encapsulation (adds ~50 bytes)
       │
       ▼
Outer UDP + IP + Ethernet headers
       │
       ▼
Physical network
```

**This reduces the space available for the inner packet if the underlay MTU is unchanged.**

**If the CNI MTU is incorrectly configured, you may see:**

- Pod-to-Pod connectivity problems.
- Large response failures.
- Intermittent service timeouts.
- **Failures across nodes but not within the same node.**

**The Kubernetes MTU gotcha:** **Setting the CNI MTU to 1500 when the overlay uses VXLAN = black hole.** Large packets fail silently; small packets work. It looks like an application bug.

### Scenario 6 — IPv6 PMTUD failure

**Symptom:** IPv6 works for small requests but fails for large ones.

**Cause:** ICMPv6 Packet Too Big is blocked (often by a firewall rule that allows ICMPv4 but not ICMPv6).

**Fix:** Allow ICMPv6 Type 2 (Packet Too Big) in firewall rules.

### Scenario 7 — Rate-limited ICMP

**Symptom:** large requests fail *intermittently* — some succeed, some fail.

**Cause:** the router sends ICMP Fragmentation Needed, but rate-limits it (e.g., to 1 per second per destination). Under load, many senders need the ICMP at once; some are dropped.

**Fix:**
- Increase ICMP rate limits (risky — DoS).
- Enable TCP MTU probing (workaround).
- Fix the MTU mismatch at the source.

### Scenario 8 — Jumbo frames mismatch

**Symptom:** datacenter nodes on 9000-MTU segments can talk to each other; cross-segment traffic fails.

**Cause:** a 9000-MTU frame must be fragmented (or dropped with DF) to cross a 1500-MTU link.

**Fix:** ensure jumbo frames are **end-to-end** (all interfaces on the path support 9000).

### Failure table

| Failure | Symptoms | Diagnosis |
|---|---|---|
| **MTU black hole** | Small requests work; large time out | `ping -M do -s 1472` fails; ICMP blocked |
| **ICMP blocked (all)** | `ping` fails; traceroute incomplete | Firewall rules |
| **ICMP Redirect allowed** | Route hijacking possible | Disable on production |
| **Router fragmentation overload** | CPU spike under load; fragment floods | Packet capture shows many fragments |
| **Jumbo frame mismatch** | Large packets fail on 9000-MTU networks | Check interface MTUs |
| **VPN MTU** | Large requests fail over VPN | Check VPN gateway MTU |
| **PPPoE MTU** | Large requests fail on DSL | 1492 or MSS clamping |
| **Kubernetes overlay MTU** | Pod-to-pod large requests fail | Check CNI MTU config |
| **IPv6 PMTUD failure** | Large IPv6 requests fail | Allow ICMPv6 Packet Too Big |
| **Rate-limited ICMP** | Intermittent large-packet failures | Check ICMP rate limits |

### Useful commands

**Windows:**

```powershell
ping 8.8.8.8
tracert 8.8.8.8
pathping 8.8.8.8

# Check interface MTU
netsh interface ipv4 show subinterfaces

# Test IPv4 with DF set and specified payload
ping 8.8.8.8 -f -l 1472
```

**Why 1472?**

```
1472 bytes ICMP payload
  8 bytes ICMP header
 20 bytes IPv4 header
──────────────────────
1500 bytes total
```

If the packet fails due to size, reduce the payload gradually, accounting for the network and destination's behavior.

**Linux:**

```bash

```

**Remember:** firewalls and ICMP filtering can affect these tests. **A failed ping alone is not conclusive.**

### Linux — allowing essential ICMP

**iptables:**

```bash

```

**ICMPv6 — allow essential types:**

## 12. REAL-WORLD ARCHITECTURE — Banking, Azure, and Kubernetes

### A. Banking platform

```
Trading API
    │
    ▼
Application subnet
    │
    ▼
Firewall
    │
    ▼
VPN / Network Gateway
    │
    ▼
External banking system
```

A large message may be segmented into multiple TCP packets. **If the path MTU is smaller than expected, the TCP connection can experience retransmissions or stalls.**

At the application level, you may see:

- HTTP timeouts.
- Slow API calls.
- Failed TLS handshakes.
- **Inconsistent behavior between small and large messages.**

**An experienced engineer should investigate the network path before changing application payload sizes or retry policies.**

### B. Azure networking

In Azure, MTU considerations become important when using:

- **VPN Gateway** — reduces MTU (typically 1350–1400 depending on SKU).
- **Site-to-site connectivity**.
- **ExpressRoute** — MTU 1500 (9000 for some SKUs).
- **Virtual network appliances**.
- **Network encapsulation**.
- **Hybrid connectivity**.

**A packet may travel through multiple network layers, each adding overhead or applying different MTU constraints.**

**Do not assume that the MTU of your VM's interface is automatically the end-to-end path MTU.**

**Azure-specific concerns:**

1. **VPN Gateway MTU is reduced** — **MSS clamping on the VPN gateway is essential.**
2. **Allow ICMP Fragmentation Needed through Azure Firewall / NSG** — Azure NSG defaults allow ICMP from within VNet; internet ICMP needs explicit rules.
3. **Azure Load Balancer** does **not** do MSS clamping. **If the backend MTU is smaller than the client's, ICMP must be allowed through.**
4. **Azure Private Endpoints** — traffic stays on the Microsoft backbone; MTU 1500 usually; PMTUD works.

### C. Kubernetes

**The overlay network MTU matters.** Different CNI plugins have different overheads:

| CNI | Overhead | Typical pod MTU |
|---|---|---|
| **Calico (BGP mode)** | 0 (native routing) | 1500 |
| **Calico (VXLAN)** | 50 | 1450 |
| **Flannel (VXLAN)** | 50 | 1450 |
| **Flannel (host-gw)** | 0 | 1500 |
| **Cilium (native)** | 0 | 1500 |
| **Cilium (VXLAN)** | 50 | 1450 |
| **Weave** | 80 (sleeve) / 0 (fastdp) | 1420 or 1500 |
| **AWS VPC CNI** | 0 | 9001 (jumbo) |

**The MTU must be correctly configured on the CNI plugin and on all nodes.** If a node has MTU 1500 but pods have MTU 1450 (due to overlay), packets between the node's own processes and the pods may exceed the path MTU.

**Diagnose with:**

```bash
kubectl exec -it pod -- ip link show eth0            # shows MTU
kubectl exec -it pod -- ping -M do -s 1422 <target>  # test path MTU
kubectl exec -it pod -- ping -M do -s 1472 <target>  # should fail if path MTU < 1500
```

### D. End-to-end flow — a payment request over VPN

1. **Client sends `POST /api/payments`** with a large payload.
2. **TCP connection** establishes (small handshake packets fit).
3. **First data packet** (1448-byte TCP segment) sent.
4. **On-prem VPN gateway** — MTU 1400. Packet is 1448 > 1400. Dropped.
5. **VPN gateway sends ICMP Fragmentation Needed** (MTU 1400) **or MSS clamping kicks in** (if configured).
6. **Client receives** — either ICMP (PMTUD) or MSS-clamped handshake.
7. **Client retransmits** at 1360 (or 1400-MSS).
8. **Success.**

**If the VPN gateway doesn't send ICMP AND doesn't clamp MSS:** step 4 repeats until timeout.

## 13. PRINCIPAL ENGINEER PERSPECTIVE

At Principal Engineer level, understand these distinctions:

| Concept | What it answers |
|---|---|
| **ICMP** | What network delivery or diagnostic information is available? |
| **MTU** | How large can one network-layer packet be on this link? |
| **MSS** | How much TCP application data fits in one segment? |
| **Path MTU** | What is the smallest MTU along the route? |
| **PMTUD** | How does the sender discover that path constraint? |
| **MSS clamping** | How can TCP segment size be constrained at network edges? |

### Five important design principles

**1. Don't block all ICMP blindly.**

Some ICMP messages are essential for correct network operation, especially ICMPv6 and PMTUD-related messages. **Security policies should allow necessary ICMP types while controlling unnecessary traffic.**

**2. Don't equate ping success with service health.**

A proper service health check should test the actual service.

**3. Understand VPN and overlay overhead.**

The effective payload capacity can be smaller than the physical interface MTU.

**4. Don't treat every timeout as an application problem.**

Investigate DNS, routing, firewall, TCP, TLS, and MTU systematically.

**5. Understand the business impact.**

**In trading and payment systems, a timeout does not mean the operation failed.** The server may have processed the transaction even though the response never reached the caller.

**Use idempotency, status checks, and correlation IDs rather than blindly retrying business operations** (Topics 38, 49).

### Additional Principal-level insights

**A. "Ping works" does not mean the network works**

`ping` uses ICMP Echo. **It tests L3 reachability with small packets.** It does **not** test:

- **MTU** — the path MTU may be smaller than the ping's size.
- **TCP port reachability** — port may be blocked (Topic 7).
- **TLS handshake** — cert issues (Topic 12).
- **HTTP reachability** — app may be down (Topic 21).
- **PMTUD** — the ICMP control path may be broken.

**Use the right tool for the right layer.** `ping` is L3 reachability. `Test-NetConnection -Port` is L4. `curl -v` is L7. **Climb the layers.**

**B. ICMP blocking is a common security decision that's often wrong**

**The common mistake:** "We block ICMP for security."

**What this actually does:**

- ✅ Prevents external `ping` scanning (minor benefit).
- ❌ Breaks `traceroute` from outside.
- ❌ **Breaks PMTUD** — the #1 cause of MTU black holes.
- ❌ **Breaks IPv6** — ICMPv6 is essential, not just diagnostics.
- ❌ Breaks customer confidence when "large uploads fail randomly."

**The Principal-level insight:** **If you block ICMP wholesale, you WILL have MTU black holes. Design the policy so the PMTUD messages flow.**

**C. MTU is a per-path property, not per-device**

**The common mistake:** "My server has MTU 1500, so all requests fit in 1500."

**Reality:** the path traverses many links, each with its own MTU. The path MTU is the **smallest** on the path.

**Where the path MTU is reduced:**

- **VPN tunnels** (IPsec, GRE, WireGuard) — 100–200 bytes overhead.
- **PPPoE** — 1492.
- **VXLAN overlays** — 1450.
- **QinQ / MPLS** — 4–8 bytes.
- **Wireless backhaul** — variable.

**The diagnostic tool:** `tracepath` (Linux) or `tracert` (Windows) with MTU probing. Or `ping -M do -s <size>` binary search.

**D. The MTU black hole is a diagnostic heuristic**

**When you see:**

- **Small requests work, large fail.**
- **`ping` works, `curl` times out on large bodies.**
- **TCP handshake succeeds; data transmission stalls.**
- **All other tests pass.**

**Think:** **MTU black hole.** Test it:

```bash
ping -M do -s 1400 <host>   # passes if path MTU >= 1428
ping -M do -s 1472 <host>   # fails if path MTU < 1500
```

**The fix is at the network layer** (allow ICMP, reduce MTU), not in the app.

**This is a Principal-level heuristic** — a fast way to recognize a problem class that most engineers spend hours diagnosing as an app bug.

**E. MSS clamping is a workaround, not a fix**

**MSS clamping** — the router rewrites the MSS in the TCP handshake to force the sender to use a smaller segment size.

**When it helps:**

- **VPN with reduced MTU + ICMP blocked** — clamping ensures packets fit.
- **Kubernetes overlay ingress** — clamping at the ingress avoids pod-level issues.

**What it doesn't fix:**

- **UDP** — no MSS; only MTU reduction (or ICMP) helps.
- **The root cause** — if PMTUD were allowed, clamping would be unnecessary.

**Prefer PMTUD. Use MSS clamping as a fallback when PMTUD can't be fixed.**

**F. IPv6 changes the rules**

**In IPv4:** routers can fragment. If PMTUD fails, oversized packets are fragmented (with performance cost).

**In IPv6:** routers **cannot** fragment. If PMTUD fails, oversized packets are **dropped**.

**The consequence:** **MTU black holes are more severe in IPv6.** A misconfigured firewall blocking ICMPv6 Packet Too Big will break IPv6 for any large packet.

**In IPv6, every firewall must allow ICMPv6 Type 2 (Packet Too Big). No exceptions.**

### Anti-patterns

| Anti-pattern | Problem |
|---|---|
| **Blocking all ICMP** | MTU black holes; traceroute broken; IPv6 broken |
| **Allowing ICMP Redirect** | Route hijacking risk |
| **No MSS clamping on VPN** | Large packets fail over VPN |
| **Kubernetes CNI MTU = 1500 with overlay** | Black hole for large pods traffic |
| **Jumbo frames across mixed segments** | Fragmentation/drop at 1500-MTU links |
| **Assuming `ping` proves everything** | Doesn't test MTU, ports, TLS, app |
| **Ignoring `tcp_mtu_probing`** | Missing safety net for black holes |
| **Not testing MTU after network changes** | VPN, tunnel, or overlay changes may introduce MTU issues |
| **No monitoring for MTU black hole symptoms** | "Large requests fail" not correlated with network changes |
| **Assuming ICMPv4 policy covers ICMPv6** | Different protocols; separate rules |
| **No path MTU discovery in QUIC/HTTP3** | QUIC has its own PMTUD — but firewalls blocking ICMPv6 break it |

### Trade-offs

| Choose | Get | Pay |
|---|---|---|
| **Allow ICMP (selective)** | PMTUD, diagnostics, IPv6 work | Some recon surface |
| **Block ICMP (wholesale)** | Reduced recon surface | MTU black holes, broken IPv6 |
| **PMTUD** | No fragmentation, correct | Dependency on ICMP |
| **Router fragmentation (IPv4 only)** | Resilience to ICMP blocking | 1988 crisis risk; CPU overhead |
| **MSS clamping** | Workaround for PMTUD failures | Doesn't help UDP; masks root cause |
| **`tcp_mtu_probing`** | Auto-recovery from black holes | Slower than PMTUD |
| **Jumbo frames** | Higher throughput | Requires end-to-end MTU 9000 |
| **Standard MTU 1500** | Universal | Lower throughput in datacenters |

### Production best practices
- **Allow ICMP Fragmentation Needed / Packet Too Big** — critical.
- **Allow Echo Request/Reply** (rate-limited) — for monitoring and diagnostics.
- **Allow Time Exceeded** — for traceroute.
- **Block Redirect, Source Quench, Echo to broadcast** — security.
- **Allow all essential ICMPv6 types** — Neighbor Discovery, Router Advertisement, Packet Too Big.
- **Configure MSS clamping on VPN gateways** — prevent black holes.
- **Set CNI MTU correctly in Kubernetes** — usually 1450 for VXLAN overlays.
- **Enable `tcp_mtu_probing=1` on Linux** — safety net.
- **Test MTU after any network change** — VPN, tunnel, overlay, jumbo frames.
- **Monitor MTU black hole symptoms** — small requests succeed, large fail, correlated with network events.
- **Use `tracepath` / `traceroute`** as first-line MTU diagnostics.
- **Document ICMP policy** — allow/block decisions, with reasons.

### The Principal Engineer's ICMP/MTU checklist

| Concern | Best practice |
|---|---|
| **Internet-facing service** | Allow ICMP Fragmentation Needed, Echo, Time Exceeded; block Redirect |
| **VPN tunnels** | MSS clamping + allow ICMP; reduce MTU on client if needed |
| **Kubernetes overlay** | Set CNI MTU correctly; allow ICMP within cluster |
| **Jumbo frames** | Only within a single L2 segment; end-to-end support needed |
| **IPv6** | Allow ICMPv6 Packet Too Big; essential for IPv6 |
| **Monitoring** | Track ICMP drops (attack indicator); track MTU black hole symptoms (small vs large request failure pattern) |
| **Diagnostics** | `ping -M do`, `tracepath` — know these tools |
| **Workaround for legacy** | `tcp_mtu_probing=1` on Linux; MSS clamping on routers |

### Decision checklist

1. Is ICMP Fragmentation Needed / Packet Too Big allowed through every firewall on the path?
2. Is ICMPv6 Packet Too Big allowed (for IPv6)?
3. Are VPN tunnels configured with MSS clamping?
4. Is the Kubernetes CNI MTU set correctly for the overlay?
5. Are jumbo frames used only within a single L2 segment?
6. Is `tcp_mtu_probing=1` enabled on Linux servers?
7. Is the ICMP policy documented (allow/block per type)?
8. Have you tested MTU on every production path with `ping -M do -s 1472`?
9. Are ICMP drops monitored (for attack detection)?
10. Is the diagnostic flow "small works, large fails → MTU" documented for the team?

## 14. INTERVIEW AND KNOWLEDGE VALIDATION — with explanations

### Basic

**Q1. What is ICMP?**  
**Internet Control Message Protocol** — a **network-layer control and error-reporting protocol** used by hosts and routers to communicate information about IP delivery and network conditions. **No ports, no connections** — carried inside IP packets. **`ping` and `traceroute` use ICMP.** ICMPv6 is essential for IPv6 operation (Neighbor Discovery, Router Advertisement).

**Q2. Does ICMP use TCP or UDP?**  
**No.** ICMP is carried **directly inside IP packets** (IP protocol number 1 for ICMPv4; next-header value 58 for ICMPv6). **ICMP has no ports** — it's a control protocol, not a transport protocol.

**Q3. How does ping work?**  
Sends an **ICMP Echo Request** and waits for an **ICMP Echo Reply**. Measures round-trip time. **Successful ping proves IP reachability to the host** — nothing more.

**Q4. How does traceroute work?**  
Sends probes with **progressively increasing TTL/Hop Limit values** (1, 2, 3, ...). Each router that drops a packet because TTL=0 sends back an **ICMP Time Exceeded** message — revealing its IP. **Each line in the traceroute output is one hop.**

**Q5. What is MTU?**  
**Maximum Transmission Unit** — the **largest payload** a link can carry in a single frame/packet without fragmentation at that link. Ethernet's standard MTU is **1500 bytes**. Different link types have different MTUs (PPPoE: 1492; VPNs: 1350–1450; jumbo frames: up to 9000). **The path MTU is the smallest MTU along a path.**

**Q6. What is MSS?**  
**Maximum Segment Size** — the **maximum TCP data payload** a TCP endpoint is willing to receive in one segment. **MSS = MTU − IP header − TCP header** (typically 1460 for 1500-byte Ethernet IPv4; 1440 for IPv6).

**MTU is per-link; MSS is negotiated per TCP connection.**

### Intermediate

**Q7. What is Path MTU Discovery?**  
**PMTUD** — a mechanism where **senders discover the smallest MTU on a path** by setting the **DF (Don't Fragment) bit** and **shrinking when they receive ICMP Fragmentation Needed / Packet Too Big**.

**How it works:** sender sends at its interface MTU with DF set. A router with a smaller MTU drops the packet and sends ICMP Type 3 Code 4 (or ICMPv6 Type 2) with the next-hop MTU. The sender shrinks and retries. **No router fragmentation.**

**Q8. What is a PMTU black hole?**  
A path where **packets up to a certain size pass, but larger packets are silently dropped** — because the **ICMP Fragmentation Needed message is blocked** by a firewall on the path.

**The signature:**
- Small requests work.
- Large requests fail (timeout).
- `ping -s 1400` works; `ping -s 1472` fails.

**The cause:** blocking ICMP breaks PMTUD. **The fix:** allow the ICMP message.

**Q9. Why is ICMPv6 important?**  
Because **IPv6 relies on ICMPv6 for essential operations**, not just diagnostics:

- **Neighbor Discovery** (IPv6's ARP equivalent).
- **Router Advertisement** (delivers the default gateway).
- **Path MTU Discovery** (Packet Too Big).
- **Multicast Listener Discovery**.

**Blocking ICMPv6 breaks IPv6.** This is why firewall rules for ICMPv4 and ICMPv6 must be designed **separately** — you can't just copy ICMPv4 rules.

**Q10. Why can small requests succeed while large requests fail?**  
The larger packets may **exceed the path MTU**, and **PMTUD feedback may be blocked or mishandled**. The router drops the packet (DF set), sends ICMP Fragmentation Needed — but if that ICMP is blocked by a firewall, the sender never learns. It retransmits the same oversized packet until timeout.

**The signature of an MTU black hole.**

### Advanced

**Q11. What is fragmentation, and why does PMTUD avoid it?**  
**Fragmentation** — splitting a packet larger than the link MTU into smaller fragments, each with its own IP header, reassembled at the destination.

**Why PMTUD avoids it:**
- **CPU cost** — fragmenting and reassembling costs CPU at each router.
- **Loss amplification** — losing one fragment forces retransmission of the entire original datagram.
- **Reassembly buffers** — the destination must hold incomplete datagrams.
- **1988 congestion collapse** — fragmentation overload nearly took down the internet.

**PMTUD** shrinks packets at the sender instead — no fragments, no reassembly, no amplification.

**Q12. What is a fragmentation needed message?**  
**ICMP Type 3 Code 4** (IPv4) or **ICMPv6 Type 2** (IPv6). It tells the sender "your packet is too big for this link — shrink it to the MTU I'm reporting."

**The message includes the next-hop MTU** (RFC 1191 extension), so the sender knows exactly how small to shrink.

**Q13. Why is PMTUD mandatory in IPv6?**  
Because **IPv6 routers cannot fragment** (RFC 8200). **Only senders can fragment** (and only if PMTUD fails). **Oversized IPv6 packets are dropped by routers.** The **only way** for a sender to learn to shrink is **ICMPv6 Packet Too Big**.

**The consequence:** **IPv6 MTU black holes are more severe** — no router fragmentation fallback. **Every IPv6 firewall must allow ICMPv6 Packet Too Big.**

**Q14. Explain the 1988 internet congestion collapse.**  
By 1988, the internet was **fragmenting itself to death**:

- Routers fragmented every large packet to fit smaller links.
- **One lost fragment discarded the entire original datagram.**
- **Senders retransmitted entire datagrams**, amplifying load.
- **Routers spent CPU on fragmentation**, not forwarding.
- **Bandwidth utilization collapsed.**

**The fix:** **PMTUD (RFC 1191)** — senders set DF; routers drop and report; senders shrink. **No fragmentation.** Plus **TCP congestion control (Jacobson, 1988)** — backing off on loss. Both were essential.

**Q15. What is `tcp_mtu_probing`, and when should you enable it?**  
A **Linux kernel feature** that **automatically discovers MTU** when PMTUD fails. It detects black holes (repeated packet loss at the same size) and **probes smaller sizes** by setting different MSS values.

**When to enable:** on servers behind networks with **unreliable ICMP** (VPNs, flaky firewalls, Azure NAT scenarios). It's a **safety net** — the primary fix is always to allow ICMP.

**When not to enable:** rarely. The overhead is small. `net.ipv4.tcp_mtu_probing=1` on Linux; often recommended for cloud instances.

### Scenario-based

**Q16. Ping works but HTTPS fails. What could be wrong?**  
Possible causes:

- **TCP 443 is blocked** — firewall rule.
- **TLS negotiation fails** — cert issues (Topic 12).
- **The API is unavailable** — service down.
- **DNS resolves to the wrong destination.**
- **Application firewall policy blocks traffic.**

**Ping only tests ICMP Echo behavior. It does not prove TCP 443 or HTTPS works.** Use `Test-NetConnection -Port 443` and `curl -v` for the next layers.

**Q17. Small API requests work but large requests time out. What's the likely cause?**  
**MTU black hole.** Classic signature: small requests fit under the path MTU; large requests exceed it and are dropped; the ICMP Fragmentation Needed message is blocked; retransmissions continue until timeout.

**Diagnose:**

1. `ping -M do -s 1472 <host>` — fails if path MTU < 1500.
2. `ping -M do -s 1400 <host>` — passes if path MTU ≥ 1428.
3. Binary search for the exact path MTU.

**Fix:**

1. **Allow ICMP Fragmentation Needed** on the path (best).
2. **Reduce MTU** on the affected interface.
3. **Enable `tcp_mtu_probing=1`** (workaround).
4. **MSS clamping on the router** (workaround).

**Q18. Traceroute shows timeouts at some hops. Does that mean those routers are broken?**  
**Not necessarily.** Routers may:

- **Filter ICMP** (drop Time Exceeded messages for security).
- **Rate-limit ICMP responses** (to prevent abuse).
- **Forward packets normally while suppressing diagnostic responses.**

**Check whether subsequent hops and the final destination respond.** If the destination responds, the "silent" hops are forwarding fine — they just don't send ICMP Time Exceeded.

**Q19. IPv6 works for small requests but fails for large ones. What's the likely cause?**  
**ICMPv6 Packet Too Big is blocked.** IPv6 has **no router fragmentation fallback** — oversized packets are dropped by routers. If the ICMPv6 Type 2 message doesn't reach the sender, the sender retransmits the same oversized packet forever.

**Fix:** **Allow ICMPv6 Type 2 (Packet Too Big)** in firewall rules. **This is mandatory for IPv6.**

**Q20. Users on VPN report "cannot upload large files." What could be wrong, and how do you fix it?**  
**Classic VPN MTU problem.** The VPN tunnel reduces the path MTU (typically to 1350–1450, depending on tunnel type). Without PMTUD working (ICMP often blocked through VPN), large uploads hang.

**Diagnose:**

1. `ping -M do -s 1400` on the VPN — works if path MTU ≥ 1428.
2. `ping -M do -s 1472` — fails if path MTU < 1500.

**Fix:**

1. **Enable MSS clamping on the VPN gateway** — safest, works for TCP.
2. **Allow ICMP through the VPN tunnel** (so PMTUD works).
3. **Reduce MTU on the VPN client interface** — manual but reliable.

**Q21. Should you block ICMP for security?**  
**Selective blocking, not wholesale.**

**Allow:**
- **Echo Request/Reply** (rate-limited) — for diagnostics.
- **Fragmentation Needed / Packet Too Big** — **critical for PMTUD.**
- **Time Exceeded** — for traceroute.
- **Destination Unreachable** — for diagnostics.
- **ICMPv6 essentials** (Neighbor Discovery, Router Advertisement, Packet Too Big).

**Block:**
- **Redirect** — route hijacking risk.
- **Source Quench** — deprecated.
- **Echo to broadcast** — Smurf mitigation.

**The Principal-level insight:** **Blocking Fragmentation Needed breaks PMTUD and causes MTU black holes.** This is one of the most common "security" decisions that causes operational failures.

**Q22. What's the difference between PMTUD and MSS clamping?**  
- **PMTUD** — the sender discovers the path MTU (via ICMP) and sizes packets accordingly. **Correct, efficient, requires ICMP.**
- **MSS clamping** — a router rewrites the MSS in the TCP handshake to force a smaller segment size. **Workaround, requires TCP, doesn't help UDP.**

**Use PMTUD when possible.** Use MSS clamping when PMTUD can't work (ICMP blocked, VPN tunnels).

**Both can coexist** — MSS clamping doesn't prevent PMTUD; it just limits the maximum.

**Q23. You have jumbo frames (MTU 9000) in your datacenter. Should you use them?**  
**Only end-to-end.** Jumbo frames improve throughput for large transfers but **break if any link on the path has 1500 MTU.** The packet is either fragmented (IPv4) or dropped (IPv6, or with DF set).

**When to use:**
- **Storage networks** (iSCSI, NFS) — large sequential transfers benefit.
- **High-throughput backend** — where traffic stays within the jumbo-capable segment.

**When not to:**
- **Any traffic that leaves the jumbo segment** — will break.
- **Internet-facing services** — universally MTU 1500.
- **Kubernetes clusters with mixed CNI configs** — misconfiguration risk.

**The Principal-level rule:** **Jumbo frames are for single-subnet traffic only. Never route them.**
